# Сесія 03 — Чат між учасниками (слайс D)

## Роль

Ти — senior full-stack інженер зі знанням Supabase Realtime і Postgres RLS. Ти працюєш
автономно за `AGENTS.md`. Пріоритет №1 — ніхто, крім учасників треду, не може прочитати
повідомлення, навіть звертаючись до Supabase напряму з anon-ключем.

## Контекст

- 3.15 уже зроблено: модель `Message`, міграція, політика SELECT через SECURITY DEFINER у схемі
  `private`, тест `e2e/messages-rls.spec.ts`. Прочитай запис 3.15 у `decisions.md`.
- Рішення 3.1: окремий приватний тред на кожну заявку (автор ↔ гравець). Груповий тред для
  парної гри (3.21) **відкладено** — не роби його.
- Записи в БД — лише через server actions + Prisma (рішення 1.2). Realtime — через Supabase-
  клієнт у браузері, тому RLS тут критичний.
- Прочитай «Нотатку передачі» з сесії 02 у `.agents/MEMORY.md`.

## Завдання

1. **3.16 Server action «надіслати повідомлення».** Лише учасник треду (автор оферти або
   гравець цієї заявки). Порожнє, задовге (ліміт — 2000 символів) або від неучасника —
   відмова, кожен випадок покрито тестом. Текст ніде не рендериться як HTML.
   Тред доступний для запису, поки заявка в статусі «запит» або «прийнято» і не минуло 7 днів
   від часу матчу; після — лише читання.
2. **3.17 UI треду.** Історія рендериться на сервері; поле вводу; нове повідомлення з'являється
   після відправки; системні повідомлення (тип `system`) візуально відрізняються. Тред
   доступний зі сторінки оферти (автору — біля кожної заявки, гравцю — біля своєї заявки).
   Перше системне повідомлення в кожному треді: «Meet at the court. Never send money in
   advance.»
3. **3.18 Realtime.** Нове повідомлення з'являється в іншому браузері без перезавантаження;
   підписка знімається при виході зі сторінки; втрата з'єднання не ламає сторінку (повідомлення
   доступне після перезавантаження).
4. **Модель системних повідомлень.** Якщо в `Message` немає типу — додай поле `type`
   (`text` / `system`) і nullable `senderId` для системних. Лише додавання, без руйнування
   даних. Функція `postSystemMessage(threadId, text)` у `lib/` — вона знадобиться в сесіях 04,
   06, 07.
5. **E2E флоу №3 (частина 2):** після прийняття заявки автор і гравець обмінюються
   повідомленням; третій користувач не бачить тред (перевір і через UI, і через supabase-js).
