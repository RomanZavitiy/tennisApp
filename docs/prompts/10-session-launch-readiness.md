# Сесія 10 — Готовність до публічного запуску (слайс J, частина 2)

## Роль

Ти — senior full-stack інженер, що готує продукт до перших сторонніх користувачів: приватність
(RODO), прозорість, спостережуваність, розділення середовищ. Частина кроків залежить від людини
— твоє завдання зробити все, що можна в коді, і дати людині точний чекліст решти. Працюєш
автономно за `AGENTS.md`.

## Контекст

- Рішення (2026-10-14):
  - Аналітика: **PostHog EU** у режимі без cookie (`persistence: 'memory'`), без персональних
    даних у подіях → cookie-банер не потрібен (6.13 закривається записом у `decisions.md`).
  - Видалення акаунта: профіль, фото, email, дата народження видаляються; тексти повідомлень →
    «[deleted]»; відкриті оферти скасовуються, заявки відкликаються; підтверджені матчі лишаються
    з «Deleted player», щоб не ламати ELO суперників.
  - Моніторинг помилок: Sentry, безкоштовний план.
  - Staging і prod — окремі проєкти Supabase.
- Людина підготувала (перевір env, і якщо чогось немає — пропусти пункт і внеси в чекліст):
  домен; ключі PostHog і Sentry; другий проєкт Supabase; тексти regulamin і політики
  приватності (якщо їх ще немає — сторінки з позначкою «Draft» і місцем для тексту).
- Прочитай «Нотатку передачі» з сесії 09.

## Завдання

1. **6.5, 6.6 Аналітика.** PostHog EU без cookie. Події: `signup_completed`, `offer_created`,
   `join_requested`, `join_accepted`, `message_sent`, `booking_outbound_clicked`,
   `court_marked_booked`, `result_confirmed`, `no_show_reported`, `push_enabled`. Жодних email,
   імен, текстів повідомлень (тест або перевірка типами, що payload не містить цих полів).
   **6.13** — закрити записом у `decisions.md`.
2. **6.19 Sentry.** Сервер і клієнт, source maps; email/ім'я користувача не передаються; DSN через
   env. Навмисна тестова помилка на preview видна в Sentry — інструкція для людини.
3. **6.14 Експорт даних.** Користувач завантажує JSON: профіль, оферти, заявки, свої
   повідомлення, матчі. Тест: експорт не містить чужих персональних даних (лише ім'я + ініціал
   суперників).
4. **6.15 Видалення акаунта** за політикою вище. Підтвердження введенням слова; після — вихід,
   вхід неможливий, профіль 404, фото видалено зі Storage. **Перед міграціями/каскадами —
   зупинись і покажи людині план змін у схемі** (це руйнівна операція з даними).
5. **6.11, 6.12 Легал.** Сторінки `/terms` і `/privacy` (EN/PL) з датою редакції, посилання у
   футері. Галочка згоди в онбордингу; зберігаються дата згоди і версія документа. Наявні
   користувачі при наступному вході бачать екран згоди.
6. **6.9, 6.10 Середовища.** Мапінг env для Preview → staging і Production → prod у README;
   процес `prisma migrate deploy` для prod — окремий ручний крок, описаний у `decisions.md`.
   Сам перенос змінних у Vercel робить людина — дай точний список.
7. **5.13 → 1.19 Домен і листи.** Якщо домен і Resend-домен готові: адреса відправника з env;
   auth-листи Supabase через Resend SMTP — інструкція для людини (налаштовується в дашборді).
   Якщо не готові — лише чекліст.

## Правила роботи

- Одна гілка `feat/slice-J2-launch-readiness`, один PR (або два: «приватність» і
  «інфраструктура», якщо diff великий).
- Нові сервіси PostHog і Sentry погоджені людиною в рішеннях — окремої зупинки не потрібно;
  додай їх у список стеку `AGENTS.md` §2 у цьому ж PR.
- Зупинка за 4 умовами з `AGENTS.md` — особливо для п. 4.

## Очікуваний результат

1. PR(и): «що і чому», ID, нові залежності, список env-змінних для кожного середовища.
2. **`docs/LAUNCH-CHECKLIST.md`** — покроковий чекліст для людини: що налаштувати в Vercel,
   Supabase (prod), Resend, DNS, PostHog, Sentry; як перевірити кожен пункт; що зробити в день
   запуску (бекап, перший `migrate deploy`, смоук-тест 4 флоу на prod).
3. `docs/PLANNING.md`: виконані ID ✅; невиконані через відсутність ресурсів людини — з
   «Залишок: …».
4. `.agents/MEMORY.md` → підсумкова нотатка: стан продукту, відомі обмеження, що робити після
   запуску (розділ «Відкладено» з `PLANNING.md`).
5. Фінальний звіт у чаті.
