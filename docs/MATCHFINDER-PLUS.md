# SpinBuddy — MatchFinder+: що взяти з Korteo (пункт 3.1 «Ігри та пошук партнерів»)

План, як перенести механіки пошуку партнера з Korteo (korteo.pl, аналіз від 2026-11-02) у SpinBuddy.
Q і R уже зроблено. Решта — план слайсів, згрупованих у сесії (розділ 6). Правила зупинки —
`AGENTS.md` §9/§10; розмір PR не обмежено (`AGENTS.md` §6, 2026-11-07). Слайси **Q–W** продовжують
нумерацію після O (клубний чат) і P (довідник тренерів, `docs/TIER2-FEATURES.md`).

Korteo — мультиспортова платформа з оплатами. SpinBuddy лишається тенісним matchFinder для Кракова
без платежів (рішення 2026-10-21). Тому беремо **механіки**, а не модель Korteo.

---

## 1. Що з 3.1 уже є, а чого немає

| Механіка Korteo | Є в SpinBuddy? | Де / що бракує |
|---|---|---|
| Створити гру (спорт, час, об'єкт, рівень, місця) | ✅ | `SparringOffer`: формат, час, тривалість, клуб/район, NTRP-діапазон, покриття, статус корту |
| Знайти гру поблизу за рівнем | ✅ | стрічка з фільтрами в URL (`lib/offers/feed-filters.ts`), сортування за ELO (`lib/matching/elo-rank.ts`) |
| Приєднатися / вийти | ✅ | `OfferJoin` (REQUESTED → ACCEPTED / DECLINED / WITHDRAWN). У Korteo вхід миттєвий, у нас — заявка, яку схвалює автор. Так і лишаємо |
| Чат для кожної гри | ✅ | приватний тред на заявку + груповий для парної гри |
| Сповіщення «нова гра під мій рівень» | ✅ | push з `lib/matching/offer-interest.ts`: ±0.5 NTRP, район, ліміт 3 на день, тихі години |
| Репутація після гри | 🟡 | ELO + надійність (no-show, пізні скасування). Немає м'якого відгуку («пунктуальний», «рівень відповідає») |
| Блокування гравця | 🟡 | тільки адмінське блокування (`blockedAt`). Особистого «не показуй мені цю людину» немає |
| Поділитися грою посиланням | 🟡 | сторінка `/offers/[id]` публічна, але немає кнопки «Поділитися» і превʼю для месенджерів |
| **Запросити конкретних гравців у гру** | ❌ | автор може лише чекати заявок |
| **Матчмейкінг: підбір кандидатів під гру** | ❌ | push іде «всім підходящим», але автор не бачить списку «кого запросити» |
| **Лист очікування (резерв), коли гра заповнена** | ❌ | статус `FULL`, далі нічого |
| **«Хочу пограти» (намір без конкретної гри)** | ❌ | щоб тебе знайшли, треба створити повну оферту |
| **«Грати зараз» (Play Now)** | ❌ | є фільтр дати й частини дня, але немає швидкого «сьогодні, найближчі години» |
| **«Зіграти ще раз» з тим самим партнером** | ❌ | — |
| **Автопропозиції гри** | ❌ | система сама не зводить людей |
| Оплата участі і повернення коштів | ⛔ не беремо | без платежів (рішення 2026-10-21) |

Беремо також дві ідеї з «engagement» Korteo, бо вони живлять матчмейкінг:
**ігрові вподобання** (дні, частина дня, райони) і **досягнення** з уже наявних лічильників.

## 2. Слайси і порядок

| Етап | Слайс | Що | Нова таблиця? | Розмір |
|---|---|---|---|---|
| 1. Швидкі перемоги | **Q** | «Зіграти ще раз» + кнопка «Поділитися» + OG-превʼю оферти | ні | S |
| | **R** | Особисте блокування гравця | так (`UserBlock`) | S–M |
| 2. Ядро матчмейкінгу | **S1** | Запрошення гравця в оферту | так (`OfferInvite`) | M |
| | **S2** | «Підібрані гравці» на своїй оферті | ні (чиста функція + запит) | M |
| | **T** | Резерв для заповненої оферти | так (`OfferWaitlist`) | M |
| 3. Доступність | **U1** | Ігрові вподобання в профілі | колонки в `User` | S–M |
| | **U2** | «Хочу зіграти» (намір) | так (`PlayIntent`) | M |
| | **U3** | «Грати сьогодні» (Play Now) | ні | S |
| 4. Пізніше | **V** | Автопропозиції гри (opt-in) | так | L |
| | **W** | Відгук після гри + досягнення | так (відгук) | M |

Чому такий порядок:
- **Q і R** не міняють основний цикл і майже не чіпають схему. Їх можна робити паралельно.
- **S1 → S2.** Підбір кандидатів без кнопки «Запросити» марний, тому S2 спирається на S1.
- **T** незалежний від S1/S2, але корисний лише тоді, коли оферти справді заповнюються.
- **U1 → U2 → U3.** Вподобання потрібні, щоб намір і Play Now показували релевантне. S1 потрібен,
  щоб автор міг запросити того, хто опублікував намір.
- **V** має сенс лише при достатній щільності гравців (орієнтир: ≥ 150 активних за тиждень).
  Раніше він буде пропонувати порожнечу.

## 3. Опис слайсів

### Q — «Зіграти ще раз» і шеринг (S, без схеми)

- **Q.1** На «Моїх іграх» (`lib/offers/my-games.ts`) у завершеного матчу з'являється кнопка
  «Зіграти ще раз». Вона відкриває форму нової оферти, заповнену з минулої: клуб/район, формат,
  тривалість, NTRP-діапазон, той самий день тижня і час, +7 днів. Предзаповнення йде через
  query-параметри, як уже зроблені фільтри стрічки.
- **Q.2** Після S1 ця ж кнопка ще й одразу запрошує минулого суперника. До S1 — лише
  предзаповнення.
- **Q.3** Кнопка «Поділитися» на `/offers/[id]`: `navigator.share` з фолбеком «Скопіювати
  посилання». Нових бібліотек не треба.
- **Q.4** Розширити наявний `generateMetadata` у `/offers/[id]` (зараз там лише загальний
  заголовок): заголовок «Спаринг, сб 18:00, NTRP 3.5–4.0,
  Подгуже» і опис для превʼю в Messenger/WhatsApp. Особистих даних у превʼю не ставимо, тільки
  ім'я автора, як і на самій сторінці.
- Тести: unit на побудову предзаповнення (дата +7 днів з урахуванням DST за Europe/Warsaw).

### R — Особисте блокування (S–M)

- **R.1** Модель `UserBlock {blockerId, blockedId, createdAt}`, `@@unique([blockerId, blockedId])`.
  Таблиця належить користувачу, як `OfferDismissal`: RLS увімкнено без політики, читає лише сервер.
- **R.2** Ефект двосторонній. Оферти заблокованого зникають зі стрічки, заявки між цими двома
  неможливі в обидва боки, нові повідомлення в їхніх тредах заборонені. Заблокований нічого не
  бачить і не отримує сповіщення.
- **R.3** Кнопка «Заблокувати» на профілі гравця і в меню треду. Список «Заблоковані» в профілі
  з розблокуванням.
- **R.4** Перевірки в `join-rules.ts`, у фільтрі стрічки і в серверній дії повідомлень. Unit-тест
  на кожне правило.
- Скарга (`Report`) і блокування — різні речі: скарга йде адміну, блокування стосується тільки тебе.

### S1 — Запрошення в оферту (M)

- **S1.1** Модель `OfferInvite {offerId, inviterId, inviteeId, status: PENDING|ACCEPTED|DECLINED|EXPIRED, createdAt, respondedAt}`,
  `@@unique([offerId, inviteeId])`. Запрошення спливає в момент `startsAt`.
- **S1.2** Прийняте запрошення створює `OfferJoin` одразу в статусі `ACCEPTED`: автор уже
  погодився, коли запрошував. Перевіряються ті самі правила, що й для заявки (місця, час, блок із R).
- **S1.3** Нові `NotificationKind`: `INVITE_RECEIVED`, `INVITE_ACCEPTED`. Push і email-фолбек
  працюють, як для `JOIN_REQUESTED`.
- **S1.4** Звідки запрошувати: кнопка «Запросити в гру» на профілі гравця (вибір із моїх
  відкритих оферт), у таблиці лідерів і в списку S2.
- **S1.5** Ліміт: нова `RateLimitAction.OFFER_INVITE`, напр. 10 на годину, щоб не було спаму.
- Тести: unit на переходи статусів запрошення (за зразком `join-transitions.ts`). E2E не додаємо:
  у §7 лише 4 потоки.

### S2 — «Підібрані гравці» (M)

- **S2.1** Чиста функція `lib/matching/candidates.ts`: на вході оферта і пул гравців, на виході
  топ-10 з причиною («рівень 3.5, твій район, надійність 96%»).
  Правила:
  - NTRP у діапазоні оферти ±0.5 (та сама константа, що в `offer-interest.ts`);
  - район збігається, а після U1 — один із бажаних районів;
  - ELO ближче до автора;
  - надійність ≥ 80% або < 3 запланованих матчів (новачків не відсікаємо);
  - виключаємо: автора, заблокованих (R), тих, хто вже подав заявку чи отримав запрошення, тих,
    хто приховав цю оферту (N), заблокованих адміном.
- **S2.2** Секція «Кого запросити» на сторінці своєї оферти: тільки для автора і тільки поки
  оферта `OPEN`. Біля кожного кандидата — кнопка «Запросити» (S1).
- **S2.3** Приватність: показуємо лише те, що вже публічне в профілі. Нова колонка
  `discoverable` (за замовчуванням true) у `User` дає змогу не з'являтися в підборі.
  **Стоп-і-спитай:** це зміна того, хто кого бачить, тож власник має підтвердити дефолт.
- Тести: unit на кожне правило ранжування і на виключення.

### T — Резерв для заповненої оферти (M)

- **T.1** Модель `OfferWaitlist {offerId, userId, createdAt}`, `@@unique([offerId, userId])`.
  Позиція — це порядок за `createdAt`, окремо не зберігається.
- **T.2** На `FULL`-оферті кнопка «Стати в резерв». Гравець бачить свою позицію і може вийти з
  резерву.
- **T.3** Коли місце звільняється (`WITHDRAWN`, `DECLINED` після `ACCEPTED` чи скасування),
  перший у черзі отримує push `SPOT_OPENED` і пріоритетну заявку, яку автор бачить зверху з
  міткою «з резерву». Авто-прийняття не робимо: автор досі вирішує сам.
- **T.4** Через 2 години без реакції місце пропонується наступному в черзі. Це робить наявний
  щогодинний cron.
- Тести: unit на просування черги.

### U1 — Ігрові вподобання (S–M)

- **U1.1** Колонки в `User`: `preferredDays` (масив днів тижня), `preferredTimes` (масив з
  `TIMES_OF_DAY`), `preferredDistricts` (масив `District`, крім основного району).
- **U1.2** Блок «Коли я люблю грати» в налаштуваннях профілю. Схема Zod, усе необов'язкове.
- **U1.3** `offer-interest.ts`: push про нову оферту враховує бажані райони і частини дня.
  Порожні вподобання означають поточну поведінку.
- Тести: unit на оновлені правила `offer-interest`.

### U2 — «Хочу зіграти» (M)

- **U2.1** Модель `PlayIntent {userId, date, times[], districts[], format, note?, expiresAt}`.
  Не більше 1 активного наміру на день на гравця; намір спливає опівночі за Europe/Warsaw.
- **U2.2** Вкладка «Шукають гру» біля стрічки оферт: картки наміру з рівнем, районами і частиною
  дня. Фільтри ті самі.
- **U2.3** На картці наміру кнопка «Запросити в мою гру» (S1), а якщо відкритої оферти немає —
  «Створити гру і запросити» (форма з предзаповненням).
- **U2.4** Push авторам відкритих оферт, які підходять під намір. Ліміт той самий, що й для
  `NEW_OFFER_FOR_LEVEL`.
- **Стоп-і-спитай:** нова таблиця, яку бачать інші гравці, а отже нова RLS-політика на читання
  (§10). Пропозиція: читає тільки сервер, клієнтського читання немає.

### U3 — «Грати сьогодні» (S, без схеми)

- **U3.1** Сторінка або секція на головній: оферти, що стартують у найближчі 1–8 годин і
  підходять під мій рівень, плюс наміри (U2) на сьогодні.
- **U3.2** Порожній стан: «Сьогодні нікого немає — створи гру на вечір» з предзаповненою формою.
  У Korteo це `play_now_empty_state` / `fallback_used`.
- **U3.3** Подія PostHog для кожного кроку (див. розділ 4), щоб бачити, чи це хтось використовує.

### V — Автопропозиції гри (L, пізніше)

Щоночі cron шукає пари сумісних гравців серед тих, хто ввімкнув opt-in. Критерії: рівень, райони,
вподобання з U1 і наміри з U2. Обом надходить пропозиція «Хочеш зіграти з X у суботу ввечері?».
Якщо обидва приймають, створюється оферта з прийнятою заявкою, а корт бронює ініціатор або
фіксується статус «WILL_BOOK». Окремий епік із власним рішенням у `decisions.md`: opt-in, частота,
ліміти, що бачить кожна сторона до згоди. Не починати, поки немає щільності (етап 2).

### W — Відгук після гри і досягнення (M, пізніше)

- Після підтвердженого результату — необов'язкові 3 теги на суперника: «пунктуальний»,
  «рівень відповідає NTRP», «приємна гра». Показуємо тільки агрегат (бейдж від 5 відгуків),
  не окремі відгуки.
- Сигнал «рівень вищий/нижчий за заявлений» допомагає калібрувати NTRP новачків до першого ELO.
- Досягнення рахуються з наявних лічильників без нової таблиці: перший матч, 10/25/50 матчів,
  «Надійний» (≥ 95%), 5 різних суперників, «регулярний місяць» (4 матчі).
- **Стоп-і-спитай:** рішення щодо приватності (що бачать інші) — запис у `decisions.md`.

## 4. Аналітика (PostHog, серверна)

Korteo міряє воронку кожної механіки. Пропоную ті самі точки для своїх рішень «залишити чи
прибрати»:

| Слайс | Події |
|---|---|
| Q | `play_again_clicked`, `offer_shared` {method: native\|copy} |
| R | `player_blocked`, `player_unblocked` |
| S1 | `invite_sent` {source: profile\|leaderboard\|candidates\|intent}, `invite_accepted`, `invite_declined`, `invite_expired` |
| S2 | `candidates_viewed` {count}, `candidate_invited` {rank} |
| T | `waitlist_joined`, `waitlist_spot_offered`, `waitlist_spot_taken`, `waitlist_spot_passed` |
| U2 | `intent_posted`, `intent_invited`, `intent_converted` (намір → гра) |
| U3 | `play_today_viewed`, `play_today_result_selected`, `play_today_empty_state` |

Головна метрика етапу 2: **частка оферт, що стали FULL** і **час до першої прийнятої заявки**.
Якщо S1/S2 не зрушують ці числа за 3–4 тижні, етапи 3–4 варто переглянути.

## 5. Рішення, які має ухвалити власник до старту

1. **S2.3** — чи потрапляє гравець у «Підібраних» за замовчуванням (`discoverable = true`)?
2. **S1.2** — прийняте запрошення одразу стає `ACCEPTED`. Альтернатива: `REQUESTED` з авто-схваленням.
3. **T.4** — скільки годин на реакцію з резерву: 2 години чи менше, якщо гра скоро?
4. **U2** — наміри бачать усі залогінені гравці чи тільки ті, чий рівень підходить?
5. **V / W** — чи взагалі робити, і коли (поріг щільності)?

## 6. Сесії і шаблон

Одна сесія робить кілька слайсів підряд, одна гілка й один PR на сесію:

| Сесія | Слайси | Примітка |
|---|---|---|
| 1 | **S1 → S2** | S2 спирається на S1, спільний код `lib/matching/`, `lib/offers/` |
| 2 | **T** | незалежний; можна паралельно з сесією 1, але в окремому worktree (обидва міняють `schema.prisma`) |
| 3 | **U1 → U2 → U3** | після сесії 1 (U2.3 використовує запрошення з S1) |
| пізніше | V, W | чекають щільності гравців |

Перед стартом сесії власник відповідає на питання з розділу 5, що стосуються її слайсів, щоб
сесія не зупинялась на «стоп-і-спитай».

Шаблон (вставляти першим у кожну сесію):

```

Read docs/MATCHFINDER-PLUS.md, sections for Slices <X, Y, ...>, and the owner decisions in
section 5. Do all listed slices back-to-back in this session without stopping between them.

Before opening files, check graphify-out/GRAPH_REPORT.md and graph.json. If HEAD is newer than
the graph's commit, run `graphify update .` once at the start.

Branch: git fetch origin main && git checkout -b feat/<x-y>-<short-name> origin/main

Done = pnpm build, lint, typecheck, test green; no console.log, commented-out code or unrelated

```
