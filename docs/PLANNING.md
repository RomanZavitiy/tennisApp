# PLANNING.md — MatchFinder Kraków, план v2 (швидкий шлях до запуску)

Цей файл замінює попередній план. Старий план перенести в `docs/archive/PLANNING-v1.md` без змін —
це історія рішень. ID задач збережені: старі задачі мають старі номери, нові отримали наступні вільні
номери у своїх epics (`1.20`, `3.22`, `4.10`...). Посилання в комітах не ламаються.

Правила розробки — у [AGENTS.md](../AGENTS.md). Слайс A оновлює AGENTS.md під полегшений процес,
описаний нижче.

## Що змінилось порівняно з v1

- **Робота йде слайсами, а не S-задачами.** Слайс — це вертикальний шматок функціональності:
  кілька ID, одна гілка, один PR, одне рев'ю людини наприкінці.
- **Усі рішення, що блокували агента (🧑), ухвалені нижче.** Їх можна змінити, але агент більше
  не чекає на них.
- **Відкладено все, що не потрібне до перших реальних користувачів** (див. «Відкладено»).
- **Додано:** статус корту в оферті, надійність гравця (неявки й пізні скасування), PWA з web
  push, польська мова до запуску, вік 18+, облік переходів на бронювання.

## Позначення

- ✅ — відмічено зробленим у v1.
- 🔎 — ймовірно зроблено (інші виконані задачі від цього залежать або v1 згадує це як наявне в
  коді). Слайс A перевіряє кожну таку позицію.
- ⬜ — треба зробити.
- ⏸ — відкладено до появи реальних користувачів, з причиною.
- **Розмір слайсу:** S — до дня · M — 1–3 дні · L — 3–5 днів роботи агента.

## Процес (полегшений)

1. **Один слайс = одна гілка `feat/<слайс>-<коротка-назва>` = один PR.** Агент виконує всі ID
   слайсу підряд і не зупиняється між ними.
2. **DoD слайсу:** `pnpm build`, `pnpm lint`, `pnpm typecheck`, `pnpm test` зелені; нова логіка в
   `lib/` має юніт-тести; у diff немає `console.log` і закоментованого коду; в описі PR — абзац
   «що зроблено і чому» плюс список ID.
3. **E2E лише для 4 критичних флоу:** (1) вхід → онбординг; (2) створити оферту → бачити в стрічці;
   (3) заявка → прийняття → повідомлення в чаті; (4) результат → підтвердження → ELO змінився.
   Інші флоу покриваються юніт-тестами.
4. **`decisions.md` — лише для незворотних рішень:** схема БД, RLS, формула ELO, приватність і
   видалення даних, нові зовнішні сервіси. Звичайні деталі реалізації описуються в PR.
5. **Агент зупиняється й питає людину лише якщо:** потрібен новий зовнішній сервіс; міграція
   видаляє або перейменовує дані; нова RLS-політика відкриває читання; потрібен секрет.
   В усіх інших випадках агент вирішує сам і пише рішення в PR.
6. **Рев'ю людини** — наприкінці слайсу, на preview-деплої.
