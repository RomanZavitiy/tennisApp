# decisions.md — журнал архітектурних рішень

Короткі датовані записи про реальні рішення (AGENTS.md §10): що вирішили і чому. Записи не
видаляються й не переписуються — якщо рішення змінюється, додається новий запис, який посилається
на старий. Нові записи — внизу.

Формат: `## YYYY-MM-DD — назва` · **Рішення** · **Чому** · (опційно) **Наслідки / посилання**.

## 2026-09-20 — MVP без системи бронювання кортів

**Рішення:** у MVP немає бронювання й оплати кортів. Сторінка клубу лише дає зовнішнє посилання
на бронювання в самого клубу.
**Чому:** головна цінність продукту — знайти партнера (matchFinder), а не замінити системи
бронювання клубів. Бронювання й платежі — великий окремий шмат роботи (інтеграції з клубами,
платіжний провайдер, повернення коштів), який відклав би запуск.
**Наслідки:** може бути переглянуто після MVP (Open Questions у плані).

## 2026-09-20 — Стек проєкту

**Рішення:** Next.js 15 (App Router) + TypeScript · Supabase (Postgres, Auth, Storage, Realtime) ·
Prisma · Tailwind CSS + shadcn/ui · react-leaflet + OpenStreetMap · React Hook Form + Zod ·
Resend · Vercel · GitHub Actions · Vitest + Playwright · pnpm.
**Чому:** один фреймворк для фронтенду й бекенду (без окремого API-сервера); один керований
сервіс замість окремих БД/auth/сховища/realtime; безкоштовні плани достатні на старті;
OpenStreetMap — без ключів і лімітів Google Maps; Zod-схема спільна для форми й сервера.
**Наслідки:** будь-яка бібліотека чи сервіс поза цим списком — лише після погодження з людиною
(AGENTS.md §2). Точні версії Next.js / Node / Prisma — окремим записом (задача 0.3).

**Чому:** без паролів — немає скидання пароля і зберігання хешів; Google — найшвидший вхід для

## 2026-09-24 — Формат оферти

**Рішення:** синґл за замовчуванням, парна гра — опційно. У парній оферті автор може позначити
«вже маю партнера»: тоді потрібно 2 гравці, інакше 3. Партнер у MVP — лише позначка, не
прив'язаний акаунт.
**Чому:** синґл — основний сценарій спарингу; парна гра потрібна частині гравців, але прив'язка
партнера-акаунта ускладнює модель без великої користі на старті. Формула — у задачі 3.1.

## 2026-09-24 — Чат

**Рішення:** окремий приватний тред на кожну заявку (автор ↔ гравець); у парній грі прийняті
учасники додатково мають спільний груповий тред.
**Чому:** приватний тред дозволяє домовитись до прийняття без розкриття телефону/email; груповий
потрібен, щоб четверо людей узгодили гру в одному місці.

## 2026-09-24 — ELO лише для синґлів

**Рішення:** рейтинг рахується лише за синґли; результати парних ігор у MVP не вносяться.
**Чому:** ELO для пар потребує окремої моделі (рейтинг пари vs індивідуальний) — це ускладнення
без чіткої користі для MVP.

## 2026-09-25 — Версії Next.js, Node і Prisma (задача 0.3)

**Рішення:** Next.js **16** (на момент рішення 16.3.x) · Node **24 LTS** (24.x) · Prisma **7**

- Prisma: npm-тег `latest` на момент рішення вказує на `8.0.0-rc` — реліз-кандидат у фундамент
  проєкту не ставимо; беремо останню стабільну 7.x і переходимо на 8 окремим PR після релізу.
**Наслідки:** AGENTS.md §2 і README оновлено на Next.js 16. Точне закріплення версії Node і
pnpm у репо — задача 0.5; Prisma ставиться з явною версією (`prisma@7`), не `@latest`.
Локально потрібно оновити Node з 20 до 24 до початку 0.4.

**Чому:** Next.js 16 під час `next dev`, коли його запускає AI-агент, сам дописує в `AGENTS.md`

## 2026-09-26 — Як закріплено Node і pnpm (задача 0.5)

**Рішення:** Node — `.nvmrc` (`24`) + `engines.node: ">=24 <25"` у `package.json` +
`engineStrict: true` у `pnpm-workspace.yaml`. pnpm — поле `packageManager: "pnpm@12.6.0"`.
`@types/node` піднято з `^20` до `^24`, щоб типи відповідали реальному рантайму.
**Чому:**
- Без `engineStrict` pnpm на невідповідному Node не показує навіть попередження — перевірено.
  З ним `pnpm install` падає з `ERR_PNPM_UNSUPPORTED_ENGINE`.
- `.nvmrc` читають nvm і `actions/setup-node` (CI, задача 0.16); `engines.node` читає Vercel, щоб
  обрати версію Node для білду.
- Інша версія pnpm не падає, а сама перемикається на версію з `packageManager` (перевірено з
  pnpm 10). Це сильніше за попередження: встановлення завжди йде тією самою версією.
- Верхня межа `<25` — щоб перехід на наступну major Node був свідомим рішенням, а не випадковістю.

## 2026-09-26 — Prettier: стандартні налаштування, без markdown, LF скрізь (задача 0.7)

**Рішення:** Prettier із налаштуваннями за замовчуванням (`.prettierrc.json` = `{}`);
`*.md` і `pnpm-lock.yaml` у `.prettierignore`; `.gitattributes` з `* text=auto eol=lf`.
**Чому:**
- Налаштування за замовчуванням — менше рішень і суперечок; код, згенерований create-next-app,
  їм уже відповідав.
- На документах Prettier переписує відступи в списках задач і розтягує таблиці: `docs/PLANNING.md`
  отримав би дифф на ~600 рядків без жодної користі. Документи пише людина — форматуємо їх руками.
- На Windows з `core.autocrlf=true` git віддає файли з CRLF, а Prettier очікує LF — локально
  `format:check` падав би на кожному файлі, а в CI (Linux) проходив би. `eol=lf` робить робочу
  копію однаковою на всіх машинах.

## 2026-09-26 — ESLint: strictTypeChecked + заборона console.log (задача 0.8)

**Рішення:** для `.ts/.tsx` увімкнено `typescript-eslint` `strictTypeChecked` (type-aware правила
через `projectService`); у `app/`, `lib/`, `components/` — `no-console` з дозволом лише на
`console.warn` і `console.error`. `typescript-eslint` додано прямою devDependency тієї ж версії,
що й у `eslint-config-next`.
**Чому:**
- `strictTypeChecked`, а не `recommendedTypeChecked`: код поки майже порожній, тож найсуворіший
  набір нічого не коштує зараз, а послабити окреме правило пізніше легше, ніж посилювати на
  готовому коді. Type-aware правила ловлять те, що людина на рев'ю легко пропустить
  (незачекані проміси, `any`, що «протікає» в типізований код).
- `console.warn/error` дозволені — це справжня діагностика (Epic 6 підключить моніторинг помилок);
  заборонено лише налагоджувальний `console.log`.
- Та сама версія `typescript-eslint` — інакше в ESLint потрапляють дві копії плагіна
  `@typescript-eslint`, і flat config падає з конфліктом плагінів.

## 2026-09-26 — Pre-commit хук: husky + lint-staged (задача 0.9)

**Рішення:** husky запускає lint-staged перед кожним комітом; для змінених `.ts/.tsx/.js/.mjs` —
`eslint --fix` і `prettier --write`, для `.json/.css/.yaml` — лише `prettier --write`.
Хук ставиться сам через скрипт `prepare` під час `pnpm install`. lint-staged — 17.5.1, не
найновіша 17.6.0.
**Чому:**
- Перевіряються лише файли в коміті — хук лишається швидким, коли проєкт виросте.
- Автовиправлення (`--fix`, `--write`) прибирає дрібниці без участі людини; справжні помилки
  (як-от `console.log`) не виправляються автоматично й блокують коміт.
- `typecheck` у хук не додано: `tsc` перевіряє весь проєкт і з ростом коду сповільнить кожен
  коміт; типи перевіряє CI (задача 0.16).
- 17.6.0 вийшла в день задачі, і pnpm відхилив її правилом `minimumReleaseAge` (захист від
  щойно опублікованих, можливо скомпрометованих версій), автоматично додавши виняток у
  `pnpm-workspace.yaml`. Виняток прибрано, взято попередню версію — правило не обходимо.

## 2026-09-28 — Як підключено Prisma 7 (задача 0.11)

**Рішення:** Prisma **7.10.0** (`prisma`, `@prisma/client`) плюс `@prisma/adapter-pg`. Клієнт
генерується в `lib/generated/prisma` (у `.gitignore`, перегенеровується в `postinstall`) і
створюється лише в `lib/db.ts`. CLI (міграції, studio) ходить через `DIRECT_URL`, а застосунок —
через `DATABASE_URL` (transaction pooler). `prisma.config.ts` читає `.env.local` вбудованим
`process.loadEnvFile` з Node. У `pnpm-workspace.yaml` дозволено install-скрипти `prisma`
(перевірка версії Node) і `@prisma/engines` (завантажує schema engine для міграцій).
**Чому:**
- У Prisma 7 клієнт працює лише через driver adapter; `@prisma/adapter-pg` — офіційний адаптер
  Prisma для Postgres, а не окрема бібліотека поза стеком.
- Prisma 7 сама не читає env-файли. Наші секрети лежать у `.env.local`, тому `.env` не заводимо,
  а замість `dotenv` беремо вбудований у Node 24 завантажувач: на одну залежність менше.
- `prisma init` не запускали: крім конфігу, він кладе свої skill-файли в `.agents/`, `.claude/`
  і `.windsurf/`, що змішалося б з нашими документами. Ті самі файли написано вручну.
- Клієнт тримаємо на `globalThis` у dev: перевірено 8 hot reload у `pnpm dev`, кількість
  з'єднань до бази лишалась 3.

## 2026-09-28 — Базова схема БД: конвенції та правила видалення (задача 0.12)

**Рішення:** каркас п'яти моделей — лише ключі, зв'язки, статуси й часові мітки; предметні поля
додають задачі 1.10, 2.1, 3.2, 3.10, 4.4. Конвенції:
- Таблиці, колонки й enum-и в Postgres — `snake_case` (`@@map`/`@map`), моделі в коді — як
  звично в Prisma (`SparringOffer`, `authorId`).
- Id — UUID, які генерує Postgres (`gen_random_uuid()`); `User.id` — це id з `auth.users` без
  зовнішнього ключа на нього. `created_at`/`updated_at` — `timestamptz` зі значенням за
  замовчуванням у БД.
- Статуси: оферта `OPEN / FULL / CANCELLED`, заявка `REQUESTED / ACCEPTED / DECLINED / WITHDRAWN`,
  результат `PENDING / CONFIRMED / DISPUTED`. Заявка унікальна для пари (оферта, гравець);
  результат — один на заявку.
- Видалення: користувач → його оферти й заявки (Cascade); оферта → її заявки (Cascade); клуб з
  офертами видалити не можна (Restrict); заявку з результатом матчу видалити не можна (Restrict).

**Чому:**
- `snake_case`: RLS-політики (1.17) і запити в SQL-редакторі Supabase пишемо руками — без лапок
  навколо кожної назви їх легше читати й менше помилок.
- UUID замість послідовних чисел: id видно в URL (`/players/[id]`, `/offers/[id]`), і за ними не
  можна перебрати всіх гравців. Значення за замовчуванням у БД — щоб рядки, вставлені не через
  Prisma (SQL-редактор, сід), теж отримували id і дати.
- Зовнішнього ключа на `auth.users` немає: Prisma керує лише схемою `public`, а підтримка кількох
  схем ускладнила б міграції. Зв'язок гарантує код (1.9), видалення акаунта — задача 6.15.
- `timestamptz`: зберігаємо UTC, показуємо в Europe/Warsaw — без плутанини з літнім часом.
- Статусу «прострочено» немає: минулі оферти ховаються за часом початку (3.20), а не фоновою
  задачею.
- Restrict на результатах: результати — історія ELO. Поки 6.15 не вирішила, що з ними робити
  (анонімізувати чи видаляти), видалення користувача, в якого є будь-який внесений результат, блокує БД,
  а не тихо стирає рейтинг суперників.
**Наслідки:** Postgres не створює індекс на зовнішній ключ сам — кожен FK покритий індексом
(окремим або унікальним). Таблиці в БД з'являться лише з першою міграцією (0.13).

## 2026-09-29 — RLS увімкнено на всіх таблицях, без політик (до задачі 1.2)

**Рішення:** окремі міграції після `init` вмикають Row Level Security на всіх п'яти таблицях і на
службовій `_prisma_migrations` без жодної політики, тобто «deny by default». Точкові політики
(Storage, Realtime) і повний ADR — у задачах 1.2 і 1.17.
**Чому:** Supabase автоматично відкриває схему `public` через Data API. Без RLS будь-хто з
публічним anon-ключем міг би читати й змінювати таблиці напряму, минаючи server actions і
перевірки в коді. Prisma підключається як `postgres`, власник таблиць, і на неї RLS не діє,
тож застосунок працює як раніше (перевірено: `anon` бачить 0 рядків, власник — усі).
**Наслідки:** кожна нова міграція, що створює таблицю, має в тому ж файлі вмикати для неї RLS:
Prisma не знає про RLS і сама цього не додасть. Команду для `_prisma_migrations` загорнуто в
перевірку існування таблиці, бо тіньова БД `migrate dev` проганяє міграції без неї.

## 2026-09-29 — Сід на чистому SQL (задача 0.14)

**Рішення:** сід — файл `prisma/seed.sql`, який `pnpm prisma db seed` запускає через
`prisma db execute`. Кожен рядок має фіксований id; `ON CONFLICT` повертає наявний рядок до
сідового статусу, а не додає копію. Клуби сід не створює — їх заповнює Epic 2.
**Чому:** сід на TypeScript потребує окремого запускача (`tsx`), бо Node не може виконати
згенерований Prisma Client напряму: у ньому імпорти без розширень. SQL-сід обходиться без

## 2026-10-03 — Спосіб входу і e2e-вхід без пошти (задача 1.1)

Деталізує запис «Вхід: magic link + Google OAuth» від 2026-09-24.

**Рішення:**
- Вхід лише через Supabase Auth: magic link на email і Google OAuth. Паролів немає —
  провайдер Email/Password для паролів не вмикаємо.
- Обидва способи повертаються в один роут `/auth/callback`, який створює сесію в cookie:
  для Google він обмінює `code` на сесію, для magic link перевіряє `token_hash` + `type`. Лист
  веде на callback з `token_hash`, а не з PKCE-кодом: PKCE-код спрацьовує лише в тому браузері,
  де ввели email, а лист часто відкривають на телефоні. Шаблон листа в Supabase змінює власник
  у задачі 1.6.
- Адресу повернення застосунок бере з origin поточного запиту, тож вхід на preview-деплої
  повертає на той самий preview, а не на production. Supabase пропускає лише адреси зі списку
  Redirect URLs: `https://spinbuddy.vercel.app/**`, `https://spinbuddy-*.vercel.app/**`,
  `http://localhost:3000/**` (`pnpm dev`) і `http://localhost:3100/**` (Playwright). Site URL —
  production.
- Один email — один акаунт: Supabase автоматично зв'язує Google-ідентичність з наявним
  користувачем, якщо email збігається і підтверджений (Google віддає лише підтверджені). Окремого
  коду для злиття акаунтів не пишемо — це перевіряє DoD задачі 1.7.
- **E2E без пошти (задача 1.18):** Playwright перед тестом створює користувача через admin API
  Supabase (`auth.admin.createUser` з `email_confirm: true`) і отримує для нього magic link через
  `auth.admin.generateLink` — цей виклик лист не надсилає, а повертає `hashed_token`. Тест
  відкриває `/auth/callback?token_hash=…&type=magiclink`, тобто проходить той самий callback, що й
  реальний користувач. Після прогону тестові користувачі видаляються (`auth.admin.deleteUser`); їх
  email має впізнаваний вигляд (`e2e-<uuid>@example.com`), щоб залишки після обірваного прогону
  можна було знайти й прибрати.
- Admin API потребує `SUPABASE_SECRET_KEY`. Його читає лише код Playwright у `e2e/`; застосунок
  його не імпортує, у Vercel його немає. Локально він лежить у `.env.local`, для e2e у CI — у
  GitHub Actions secrets (коли e2e потрапить у CI).

**Чому:**
- Без паролів немає скидання пароля, зберігання хешів і перебору паролів; magic link + Google
  покривають усіх користувачів.
- Один callback — одне місце, де створюється сесія і (з 1.9) рядок `User`, незалежно від способу
  входу.
- Відкинуті варіанти e2e-входу: пароль для тестового користувача — довелося б увімкнути вхід за
  паролем і в production; читання пошти (Inbucket/Mailpit) — є лише в локальному Supabase, а ми
  працюємо з хмарним; запис cookie сесії напряму — формат cookie внутрішній для бібліотеки
  Supabase, і тест минав би callback, який якраз треба перевіряти. `generateLink` не витрачає
  ліміт вбудованого SMTP (кілька листів на годину до задачі 1.19).

**Наслідки:** preview і production поки ділять один проєкт Supabase (запис про 0.18), тож
тестові користувачі з'являються в тому самому `auth.users`, що й справжні, — прибирання після
прогону обов'язкове, а не «бажане». Redirect URLs і шаблон листа живуть у дашборді Supabase, не в
git; якщо зміниться домен (5.13) чи порт, їх треба оновити вручну.

## 2026-10-03 — Стратегія RLS разом із Prisma (задача 1.2)

Продовжує запис «RLS увімкнено на всіх таблицях, без політик» від 2026-09-29.

**Рішення:**
- Усі читання й записи даних застосунку — на сервері через Prisma: Server Components читають,
  server actions змінюють. Браузер не ходить у таблиці `public` напряму через supabase-js (ні
  publishable-ключем, ні з сесією користувача).
- RLS у `public` — «deny by default» для ролей `anon` і `authenticated`: RLS увімкнено на кожній
  таблиці, політик немає. Таблиця без політики — норма, а не недогляд.
- Точкові політики з'являються лише там, де браузер справді говорить із Supabase сам:
  - **Storage** (задача 1.13): bucket `avatars`. Читання публічне; писати, замінювати й видаляти
    файли користувач `authenticated` може лише у своїй папці — перший сегмент шляху дорівнює
    `auth.uid()`. Файл браузер вантажить у Storage напряму, а шлях до нього в `User` записує
    server action, перевіривши, що шлях починається з id цього користувача.
  - **Realtime** (задачі 3.15–3.18): якщо чат слухатиме зміни таблиці, потрібна політика
    `SELECT` для `authenticated` лише на таблиці повідомлень і лише для учасників треду. Writes
    і там ідуть через server action. Конкретний вигляд політики — рішення 3.15.
- Кожна нова таблиця вмикає RLS у тій самій міграції (правило з запису 2026-09-29 лишається).
  Нова політика на таблиці `public` — лише окремою міграцією з поясненням у `decisions.md`.

**Де діє RLS, а де авторизацію робить код:**

| Шлях до даних | Роль у Postgres | Хто перевіряє доступ |
| --- | --- | --- |
| Prisma (Server Components, server actions) | `postgres`, власник таблиць — RLS не діє | код: `requireUser()` (1.5) і умова власника в запиті |
| supabase-js з publishable-ключем, без сесії | `anon` | RLS: у `public` — нічого |
| supabase-js із сесією користувача | `authenticated` | RLS: у `public` — нічого; Storage/Realtime — політики вище |
| supabase-js із `SUPABASE_SECRET_KEY` | `service_role` — RLS не діє | лише e2e-хелпер (1.18), застосунок цей ключ не має |

Звідси правила для коду, бо RLS тут не підстрахує:
- Кожна server action спершу викликає `requireUser()`: middleware (1.4) server actions не
  захищає.
- Зміна чужого рядка відсікається в самому запиті — `where` містить і `id`, і власника
  (`authorId: user.id`), а не лише `id` з форми.
- Приватні поля (дата народження з 1.10) не потрапляють на публічні сторінки: запити для чужого
  профілю роблять явний `select` потрібних полів, а не віддають рядок `User` цілком. RLS діє на
  рядки, не на колонки, і на Prisma не діє зовсім.

**Чому:**
- Prisma підключається як власник таблиць, тож політики RLS на неї не впливають. Якби доступ
  описували політиками, правила жили б у двох місцях (SQL-політики і код), а перевіряла б їх
  лише половина запитів. Один шлях до даних — одне місце, де читати й тестувати авторизацію.
- Supabase відкриває `public` через Data API кожному з publishable-ключем, який вшитий у
  клієнтський бандл. «Deny by default» закриває цей шлях повністю, навіть якщо в коді колись
  з'явиться помилка.
- Storage і Realtime працюють лише через Supabase-клієнт і перевіряють доступ лише політиками —
  обійти їх через Prisma неможливо, тому там політики обов'язкові. Пряме завантаження в Storage
  ще й обходить ліміт тіла запиту функцій Vercel (4,5 MB), менший за ліміт фото.

**Наслідки:**
- Задача 1.17 зводиться до перевірки: RLS уже ввімкнено міграціями від 2026-09-29, лишається
  скрипт або тест, що anon- і authenticated-запити через supabase-js до кожної таблиці `public`
  повертають порожньо.
- Рев'ю кожної server action перевіряє `requireUser()` і умову власника — це головний механізм
  авторизації, а не другий рубіж.

- Форми — React Hook Form + Zod через офіційний адаптер `@hookform/resolvers`. Схема лежить у

  щоб помилку показував Zod, а не вбудована валідація браузера.
- `/auth/callback` розбирає параметри через `parseCallbackParams()` (`lib/auth/callback.ts`):
  `code` — Google, `token_hash` + `type` (`email` / `magiclink` / `signup`) — magic link. Помилка
  Supabase, невідомий тип чи прострочене посилання → `/login?error=link` із повідомленням, а не
  500.
- Шаблони листів **Confirm signup** і **Magic Link** у Supabase (Authentication → Emails)
  посилаються на `{{ .RedirectTo }}&token_hash={{ .TokenHash }}&type=email`. `RedirectTo` —
  це `https://<поточний origin>/auth/callback?next=…`, який задає server action; він завжди
  містить `?`, тому далі йде `&`. Новому користувачу Supabase шле Confirm signup, наявному —
  Magic Link, тож міняються обидва.
**Чому:** без адаптера довелося б писати власний resolver для Zod — той самий код, лише наш.
Посилання з `token_hash` працює в будь-якому браузері (див. запис 1.1).
**Наслідки:** якщо origin деплою не входить у Redirect URLs, Supabase підставить Site URL без
`?next=…`, і посилання з листа зламається. Тому новий домен (5.13) спершу додається в Redirect
URLs. Шаблони живуть лише в дашборді Supabase.

## 2026-10-04 — Вихід лише на цьому пристрої; header читає сесію (задача 1.8)

**Рішення:** «Sign out» — server action `signOut()` (`app/auth/actions.ts`), що викликає

**Як це лягло в схему:** у `clubs` додано `slug` (унікальний), `name`, `address`, `district`,
`latitude`/`longitude` (`double precision`), `court_count`, `surfaces`, `indoor`, `verified_at`

**Чому так:**
- **Покриття масивом, «криті» окремо.** Клуб у Кракові часто має і мачку, і хард, а взимку

  `surface` згодом візьме оферта (3.2), тож його визначено один раз тут.
- **`slug` — стабільний ключ для завантаження даних (2.3).** `id` генерує Postgres, у файлі
  `prisma/data/clubs.json` його немає, тож за ним не впізнати «той самий клуб» при повторному
  завантаженні. `slug` власник вписує у файл сам (`kks-nadwislan`); upsert за ним оновлює
  наявний рядок, і `id` — а з ним посилання `/clubs/[id]` і оферти, прив'язані до клубу, — не
  змінюється. Перейменування клубу — це зміна `name`, а не `slug`.
- **`verified_at` — дата, коли власник востаннє звірив дані з джерелом.** Ціни й телефони
  застарівають; сторінка клубу (2.8) покаже «Info checked on …», щоб гравець знав, наскільки
  свіжі дані, і перепитав у клубу, якщо вони давні. Тип `date`, бо перевірка — подія дня, а не
  моменту. Саме джерело (посилання, звідки взято дані) лишається у файлі даних (DoD 2.2) і в БД
  не потрібне — користувачам воно нічого не додає.
- **Координати — `double precision`, не PostGIS.** Для ~15 маркерів на карті просторові запити
  не потрібні; нова розширена залежність БД не виправдана.
- **CHECK-обмеження в міграції**, яких не виразити в `schema.prisma`: формат `slug`; назва й
  адреса не з самих пробілів; координати в межах Землі; кортів > 0; `surfaces` не NULL, не
  порожній і без NULL-елементів (Prisma робить колонку-масив nullable, тож обов'язковість
  тримає CHECK); `website_url` і `booking_url` починаються з `http://` або `https://` — сторінки

  Вужчі правила (координати в межах Кракова, без повторів у `surfaces`) — у Zod-схемі 2.3.
  Перевірено на dev-БД у транзакціях з відкатом: валідний рядок проходить, кожне з порушень
  відкидає свій CHECK, невідоме покриття — сам enum.

**Наслідки:** міграцію застосовано до dev-проєкту Supabase, спільного поки з preview і
production (запис про 0.18) — безпечно, бо зміни лише адитивні, а таблиця порожня. Нова таблиця
не з'явилась, тож RLS-тест (1.17) змін не потребує. `seed.sql` не змінюється: він клубів не
створює (запис про 0.14). Назви покриттів і `indoor` для показу додасть задача, що вперше їх
показує (2.8).

- **Спершу весь файл, потім запис.** Схема перевіряє кожен запис і кидає одну помилку зі
  списком усіх поганих клубів за назвою (або номером, якщо назви немає), тож зламаний файл
  виправляють за один прохід, а до бази нічого не доходить. Повтор `slug` у файлі — теж помилка.
- **Правила лише в Zod:** координати в межах Кракова (прямокутник навколо міста з запасом),
  без повторів у `surfaces`, `verifiedAt` не в майбутньому (календар Кракова, як у профілі),
  `source` — обов'язкове http(s)-посилання (DoD 2.2). Схема строга: незнайомий ключ (`phnoe`)
  — помилка, а не тихо загублене поле. `source` і `todo` у БД не пишуться.
- **Клуби, яких немає у файлі, не видаляються.** На клуб можуть посилатися оферти
  (`onDelete: Restrict`), тож прибрати клуб — окремий свідомий крок.

**Перевірено:** на dev-БД у транзакції з відкатом: два запуски дають 20 рядків, а не 40;
`id` після повторного запуску той самий; змінені `courtCount` і `phone` оновлюються. Скрипт на

**Наслідки:** клуби в базі з'являться лише після ручного запуску `pnpm clubs:load`. Поки

## 2026-10-07 — Карта клубів: Leaflet лише в браузері, явна іконка маркера (задача 2.4)

**Рішення:** додати `leaflet` (1.9.4) і `react-leaflet` (5.0.0) у `dependencies` та
`@types/leaflet` (1.9.22) у `devDependencies`. Обидві бібліотеки вже є в стеку AGENTS.md. Карта —
`components/club-map/`: `club-map.tsx` рендерить саму карту, `index.tsx` — обгортка, через яку її

«© OpenStreetMap contributors» і посиланням на `openstreetmap.org/copyright`.

**Чому так:**
- **`@types/leaflet` потрібен.** У `leaflet` 1.9 немає власних типів, а `.d.ts` react-leaflet
  імпортують їх з `leaflet` — без пакета TS strict не збирається. Build-скриптів у цих пакетів
  немає, тож `allowBuilds` не змінювався.
- **SSR вимкнено через `next/dynamic(..., { ssr: false })` у клієнтській обгортці.** Leaflet
  звертається до `window` вже під час імпорту, тож модуль карти не можна навіть завантажувати на
  сервері. У Next 16 `ssr: false` дозволено лише в Client Components, тому `dynamic` живе в
  `index.tsx` з `"use client"`, а Server Components (2.6) імпортують тільки його і передають дані
  клубів пропсами. Поки модуль вантажиться, на місці карти — плейсхолдер тієї ж висоти.
- **Іконка маркера — явний `L.icon` з PNG у `public/leaflet/`.** Стандартна іконка Leaflet шукає
  картинки за шляхом з `leaflet.css`, а після бандлера цей шлях ламається. Глобальний хак
  (`delete L.Icon.Default.prototype._getIconUrl` + `mergeOptions`) чіпає приватний API, тому кожен
  маркер отримує свою іконку явно. Імпорт PNG з `leaflet/dist/images` не підійшов: Turbopack
  віддає для файлу з `node_modules` рядок-URL, а не `StaticImageData`, яку обіцяють типи Next, —
  `.src` у браузері був `undefined`, і сторінка падала з «iconUrl not set». Тож три PNG (разом
  ~4,5 КБ) скопійовано з `leaflet` 1.9.4; при оновленні Leaflet їх варто звірити.
- **`isolate` на контейнері карти.** Панелі й кнопки Leaflet мають z-index до 1000 і без
  окремого контексту накладання вилазили б поверх мобільного меню.

**Перевірено:** `pnpm build` без `window is not defined`; e2e `clubs-map.spec.ts` (карта, тайли
OSM, посилання атрибуції, жодної помилки в браузері); на production-збірці з тимчасовим маркером
іконка й тінь завантажуються (25×41 і 41 px), мобільне меню перекриває карту.

**Наслідки:** `/clubs` поки показує карту без маркерів; маркери клубів з попапом додасть 2.5.

## 2026-10-08 — Сторінка `/clubs`: список + карта, перемикач на мобільному (задача 2.6)

**Як зроблено:** сторінка (Server Component) читає клуби один раз і віддає ті самі дані списку

клієнтський шматок: на десктопі (`lg`) список і карта поруч, на телефоні кнопки List/Map

- **Перемикач — стан у клієнті, а не `?view=map` у URL.** Перемикання через URL щоразу

списку з картою — 2.7, туди ж природно перейде стан вибраного клубу в `ClubsView`.

## 2026-10-11 — Модель оферти і чату (задача 3.1)

Деталізує записи «Формат оферти» і «Чат» від 2026-09-24.

**Рішення — оферта:**
- Формат — enum `SINGLES / DOUBLES`, за замовчуванням `SINGLES`. Позначка «вже маю партнера»
  (`hasPartner`, за замовчуванням `false`) має сенс лише для `DOUBLES`: `CHECK` у міграції
  (3.2) і Zod-схема (3.3) не пускають `hasPartner = true` при синґлі.
- Автор — не заявка: він учасник гри за визначенням, у `OfferJoin` його рядка немає. Партнер
  автора — лише позначка, теж без рядка й без акаунта.
- **Скільки гравців потрібно** (окрім автора і його партнера) — одна функція в `lib/` (3.2):

  | Формат | `hasPartner` | Потрібно гравців |
  | --- | --- | --- |
  | `SINGLES` | — | 1 |
  | `DOUBLES` | `false` | 3 |
  | `DOUBLES` | `true` | 2 |

  Вільних місць = потрібно − кількість заявок `ACCEPTED`.
- Кількість потрібних гравців у БД не зберігається — її завжди обчислює функція з формату й
  позначки. Статус `FULL` зберігається: його ставить прийняття заявки (3.12) у тій самій
  транзакції, коли прийнятих стає стільки, скільки потрібно. Якщо прийнятий гравець відкликає
  заявку до гри, оферта повертається в `OPEN` (точна таблиця переходів — 3.12).

**Рішення — чат:**
- Два види тредів, обидва без окремої таблиці «тред» — тред однозначно визначає те, до чого він
  прив'язаний:
  - **приватний** — на кожну заявку (`OfferJoin`): автор ↔ гравець заявки. Існує з моменту
    подання заявки, у синґлі й у парній грі;
  - **груповий** — на парну оферту (`SparringOffer` з `DOUBLES`): автор і гравці із заявкою
    `ACCEPTED`. З'являється після першого прийняття (3.21); у синґлі його немає.
- Одна таблиця повідомлень (3.15): у кожного повідомлення заповнене рівно одне з
  `offerJoinId` / `offerId` (`CHECK`). Читати можуть лише учасники треду — це й політика RLS для
  Realtime (3.15), і умова в запитах Prisma.
- Хто втрачає доступ: гравець, чию заявку відхилили або який її відкликав, — до групового треду
  (3.21). Приватний тред лишається видимим обом сторонам як історія домовленості; чи можна в
  нього писати після `DECLINED`/`WITHDRAWN` — правило server action 3.16.
- Телефон і email у чаті й на сторінці оферти не показуються — тред і є каналом зв'язку.

**Чому:**
- Автор і партнер поза `OfferJoin`: інакше довелося б мати заявки без гравця-акаунта і
  виключати їх із підрахунку місць, ELO (4.x) та чатів.
- Обчислювати, а не зберігати «потрібно гравців»: формула з трьох рядків не може розійтися з
  даними. `FULL` зберігаємо, бо стрічка (3.6) і карта (2.9) фільтрують за ним, і рахувати
  заявки в кожному запиті стрічки дорожче й складніше.
- Без таблиці тредів: учасники треду й так виводяться із заявки чи оферти. Окрема таблиця
  дублювала б це знання, і її довелося б синхронізувати при кожній зміні статусу заявки — а
  саме від списку учасників залежить політика RLS.
- Груповий тред втрачає відхилених і тих, хто відкликав заявку, бо там домовляються четверо, хто
  справді грає; приватний — це розмова двох людей, і забирати її історію в одного з них немає
  причини.

**Посилання:** 3.2 (поля оферти й функція), 3.3 (схема), 3.10 (заявка), 3.12 (переходи статусів
і `FULL`), 3.15–3.16 (повідомлення, RLS), 3.21 (груповий тред).

## 2026-10-11 — Поля оферти (задача 3.2)

Продовжує запис «Модель оферти і чату» (3.1).

**Рішення власника:** NTRP-діапазон `ntrpMin`/`ntrpMax` — та сама шкала, що в профілі (1.5–7.0,
крок 0.5), обидва необов'язкові («будь-який рівень»); покриття — одне необов'язкове значення з
`Surface`; район і клуб — обидва nullable, але хоча б одне заповнене; коментар — до 500
символів; лише час початку, без тривалості.

**Як це лягло в схему:** enum `offer_format` (`SINGLES` / `DOUBLES`), у `sparring_offers` —
`format`, `has_partner`, `starts_at` (`timestamptz`, NOT NULL), `district`, `ntrp_min`,

CHECK-обмежень: партнер лише в парній; клуб або район; кожна межа NTRP у шкалі; min ≤ max;
коментар не з самих пробілів. Перевірено SQL-блоком із відкатом: невалідні рядки БД відкидає,
валідні — ні. Скільки гравців потрібно — `playersNeeded()` у `lib/offers/players-needed.ts`.

**Чому так:**
- **Наявні рядки заповнює сама міграція.** У dev-БД (спільній для preview і production, запис
  0.18) була оферта із сіду. `starts_at` додається nullable, отримує `created_at` — оферта
  вважається минулою і не потрапить у стрічку, — і лише тоді стає NOT NULL; оферта без клубу
  отримує район автора. Так міграція проходить у будь-якому середовищі, без ручного видалення.
- **«Час у майбутньому» не CHECK:** умова залежить від поточного часу, а CHECK має бути незмінним
  у часі — це правило Zod-схеми (3.3), як вік у профілі (1.10).
- **Район при клубі не обов'язковий:** клуби за містом району не мають (запис 2.11). Що вибір
  клубу підставляє його район — поведінка форми (3.5), БД узгодженість не перевіряє.

**Наслідки:** сід (0.14) тепер описує оферту як зіграну: `starts_at` у минулому, статус `FULL`,
бо її єдине місце зайняв Bob (модель 3.1). Міграцію застосовано до dev-проєкту Supabase.

## 2026-10-11 — Zod-схема оферти і час у Кракові (задача 3.3)

**Як зроблено:** `offerSchema` (`lib/validation/offer.ts`) — одна схема для форми (3.5) і
server action (3.4), як у профілю. Час початку приходить рядком `YYYY-MM-DDTHH:mm` (так його дає
`<input type="datetime-local">`) і означає час у Кракові; `krakowLocalToDate()`
(`lib/offers/krakow-time.ts`) переводить його в UTC-момент для БД, `toKrakowLocal()` — назад.

**Чому так:**
- **Час тлумачить сервер, а не браузер.** Браузер знає лише свій пояс: гравець, який створює
  оферту з телефона з іншим поясом, зсунув би її на години. А Vercel працює в UTC, тож `new
  Date(local)` на сервері помилявся б на 1–2 години. Пояс Кракова фіксований — Europe/Warsaw.
- **Без бібліотеки дат:** Краків — завжди UTC+1 або UTC+2, тому достатньо спробувати обидва
  зсуви й перевірити через `Intl`, який дає назад той самий час. Година, якої немає (перехід на
  літній час у березні), — помилка; година, що повторюється в жовтні, читається як перша.
- **Порожнє значення = не вказано.** Форма надсилає `""` за незайманий select чи порожній
  коментар; схема перетворює його на «немає», щоб server action не залежала від того, як саме
  форма передає порожнечу. Коментар обрізається, і лише пробіли — теж «немає» (як CHECK 3.2).
- **Помилки на конкретних полях:** «ні клубу, ні району» — на `district`, `min > max` — на
  `ntrpMax`, «партнер у синґлі» — на `hasPartner`, щоб форма показала їх поруч із полем.

**Наслідки:** верхньої межі «не далі ніж через N днів» немає — це не вирішувалось; якщо
знадобиться, додається в схему окремо.

## 2026-10-11 — Стрічка `/offers` (задача 3.6)

**Як зроблено:** `getOfferFeed()` (`lib/offers/feed.ts`) читає оферти `OPEN` з `starts_at` у
майбутньому, найближчі першими, сторінками по 20; сторінка — `/offers` (публічна) з карткою
`OfferCard`. Картка показує час у Кракові, формат, скільки місць лишилось, місце, рівень,
покриття й ім'я автора і веде на `/offers/[id]` (з'явиться в 3.13).

**Чому так:**
- **Пагінація зсувом (`?page=N`), а не курсором.** Номер сторінки в URL — простий, ним можна
  поділитися, і фільтри 3.7 житимуть поруч у тому ж URL. Ціна: якщо між переходами з'явиться нова
  оферта, одна картка може зсунутися на іншу сторінку — для дошки з десятками оферт це
  прийнятно; курсор — якщо стрічка стане довгою. Один зайвий рядок (`take: 21`) показує, чи є
  наступна сторінка, без окремого `count`. `id` у сортуванні — щоб оферти з однаковим часом не
  мінялися місцями між сторінками.
- **Вільні місця рахує запит, а не колонка:** `_count` прийнятих заявок мінус
  `playersNeeded()` (модель 3.1). Запит один на сторінку, без N+1.
- **Явний `select`:** сторінка публічна, Prisma обходить RLS (запис 1.2) — з автора йде лише
  `id` і ім'я.
- **`connection()`:** стрічка змінюється постійно, тож сторінка рендериться на кожен запит, а не
  при збірці (як `/clubs`, запис 2.5).

**Наслідки:** e2e 3.5 тепер перевіряє й стрічку (план оновлено в 3.5). E2E знаходять свої
оферти за унікальним ім'ям автора: БД спільна, рахувати картки не можна. Вставка кількох рядків
через supabase-js без `defaultToNull: false` пише `null` замість значень за замовчуванням БД.

## 2026-10-11 — Заявка на оферту: server action `requestToJoin` (задача 3.11)

**Правила** — чиста функція `joinRefusal()` (`lib/offers/join-rules.ts`), кожне з тестом:
не можна на власну оферту; на ту, що вже почалась або минула; на не `OPEN` (`FULL`,
`CANCELLED`); удруге, поки перша заявка `REQUESTED` чи `ACCEPTED`; після відхилення автором
(`DECLINED`). Після власного відкликання (`WITHDRAWN`) — можна знову: той самий рядок
повертається в `REQUESTED` (унікальність пари, запис 3.10). Правило щодо `DECLINED`/`WITHDRAWN`
запропоноване агентом і власник його не оскаржив; змінюється в одному місці.

**Як зроблено:** `requestToJoin` (`app/offers/[id]/actions.ts`, поруч із майбутньою сторінкою
3.13) — `requireOnboardedUser()`, перевірка UUID, читання оферти й наявної заявки, правила,
запис. Відповідь — лише `ok` або текст відмови, без даних жодної сторони: зв'язок — у приватному
треді заявки (3.1), не телефоном чи email.

**Чому так:**
- **Подвійний клік не створює другу заявку.** Новий рядок вставляє `createMany({ skipDuplicates
  })` — у Postgres це `ON CONFLICT DO NOTHING` на парі (оферта, гравець), тож паралельний запит
  отримує `count = 0` замість помилки унікальності. Повторна заявка після відкликання оновлює
  рядок лише за умови, що він досі `WITHDRAWN`. Перевірено на dev-БД: друга вставка — `count 0`.
- **Профіль обов'язковий** (як для створення оферти, 3.4): автор має бачити, хто просить.
- **Оферта може стати `FULL` між перевіркою і записом** — це нормально: заявка лишиться
  `REQUESTED`, а прийняти понад потрібну кількість не дасть 3.12.

## 2026-10-11 — Прийняття, відхилення й відкликання заявки (задача 3.12)

**Таблиця переходів** (`lib/offers/join-transitions.ts`, тест на кожну пару дія × статус):

| Дія | Хто | Звідки → куди |
| --- | --- | --- |
| прийняти | автор | `REQUESTED` → `ACCEPTED` |
| відхилити | автор | `REQUESTED` → `DECLINED` |
| відкликати | гравець | `REQUESTED` або `ACCEPTED` → `WITHDRAWN` |

Подати заявку знову після `WITHDRAWN` — правило 3.11. Решти переходів немає: прийняту заявку
автор не відхиляє, відхилену не приймає.

**Коли дію не можна виконати:** прийняти — якщо оферта скасована, уже почалась або всі місця
зайняті; відкликати — якщо оферта скасована або вже почалась (після початку склад — це історія, на
нього спиратимуться результати Epic 4). Відхилити відкриту заявку можна завжди, навіть на
заповненій чи минулій оферті, щоб автор міг відповісти кожному.

**Статус оферти:** `offerStatusFor()` — `FULL`, коли прийнятих стільки, скільки потрібно
(`playersNeeded()`, 3.2), і знову `OPEN`, коли прийнятий гравець відкликає заявку (модель 3.1).
Тести — для синґлу (1) і обох варіантів парної (3 і 2). Заявки, що чекали, коли оферта
заповнилась, лишаються `REQUESTED`: якщо місце звільниться, автор зможе їх прийняти.

**Як зроблено:** `acceptJoin`, `declineJoin`, `withdrawJoin` (`app/offers/[id]/actions.ts`)
мають один шлях `changeJoin`. Він перевіряє, що діє автор (або сам гравець для відкликання), —
чужу заявку не відрізнити від неіснуючої, — і в одній транзакції блокує рядок оферти (`SELECT …
FOR UPDATE`), заново читає статус заявки й кількість прийнятих, застосовує правила і пише заявку
та, якщо треба, статус оферти.

**Чому блокування:** без нього два одночасні «Accept» на останнє місце обидва побачили б його
вільним, і синґл отримав би двох суперників. Блокування рядка оферти ставить зміни однієї
оферти в чергу; інші оферти не чекають. Перевірено на dev-БД через пулер Supabase: друга
транзакція отримує блокування лише після завершення першої.

## 2026-10-11 — Сторінка оферти `/offers/[id]` (задача 3.13)

## 2026-10-11 — Стартовий ELO з NTRP (задача 4.1)

**Рішення власника:** стартовий ELO лінійно залежить від самооцінки NTRP — кожні 0.5 NTRP = 100
очок, NTRP 4.0 = 1500.

| NTRP | 1.5 | 2.0 | 2.5 | 3.0 | 3.5 | 4.0 | 4.5 | 5.0 | 5.5 | 6.0 | 6.5 | 7.0 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| ELO | 1000 | 1100 | 1200 | 1300 | 1400 | 1500 | 1600 | 1700 | 1800 | 1900 | 2000 | 2100 |

**Як зроблено:** `startingElo()` і таблиця `STARTING_ELO` у `lib/rating/starting-elo.ts`; тест
на кожен крок шкали і на значення поза нею (`RangeError`).

**Чому так:**
- **100 очок на пів рівня:** за стандартною формулою ELO (шкала 400) різниця 100 означає ~64%
  шансів сильнішого — правдоподібно для гравців, що різняться на 0.5 NTRP. Центр 1500 — звична
  точка відліку ELO.
- **Таблиця, а не формула в коді:** це рішення власника, і таблицю легше прочитати й змінити,
  ніж формулу; тест звіряє, що в ній рівно ті рівні, які пропонує профіль.
- **Поза шкалою — помилка, а не здогадка:** схема профілю (1.11) і CHECK у БД (1.10) пропускають
  лише шкалу, тож інше значення означає баг, який краще побачити одразу.

**Наслідки:** 4.2 зберігає ELO в `User` і проставляє його з цієї таблиці під час онбордингу;
ранжування стрічки (3.8–3.9) спирається на збережений ELO. Порядок узгоджено: 4.2 → 3.8 → 3.9.

## 2026-10-11 — ELO і лічильник матчів у `User` (задача 4.2)

**Як зроблено:** у `users` дві колонки — `elo` (`integer`, nullable, як решта профілю до
онбордингу) і `matches_played` (`integer`, за замовчуванням 0). Онбординг записує
`startingElo(selfRatedNtrp)` (4.1); редагування профілю з новим NTRP оновлює ELO лише доки
`matches_played = 0`. Міграція лише додає колонки; гравцям, які вже пройшли онбординг, ELO
заповнюється формулою, що відтворює таблицю 4.1 (перевірено на всій шкалі).

**CHECK-обмеження:** `elo > 0`, `matches_played >= 0`, і в кожного гравця з
`onboarding_completed_at` є `elo` — стрічка ранжує за ним (3.8). Перевірено на dev-БД блоком із
відкатом; сідові Alice і Bob отримали 1400 і 1500.

**Чому так:**
- **Поки матчів немає, ELO — це лише інша форма NTRP.** Гравець, який недооцінив чи переоцінив
  себе, виправляє рівень у профілі, і стартовий рейтинг іде слідом. Після першого підтвердженого
  матчу рейтинг рухають лише результати (4.8), інакше зміною NTRP можна було б «скинути» поразки.
  Умову `matches_played = 0` перевіряє сам запит (`updateMany`), тож вона діє навіть при гонці
  з підтвердженням матчу. Закріплено тестом server action і e2e на справжній БД.
- **Онбординг пише лише першого разу** (`where: onboardingCompletedAt: null`). Server action —
  публічний endpoint; повторний виклик раніше лише перезаписав би профіль, а тепер скинув би й
  рейтинг гравця з матчами. Повторний виклик тепер нічого не змінює й веде на головну.
- **`matches_played` зберігається, а не рахується з результатів:** його оновить та сама
  транзакція, що застосовує ELO (4.8), і він потрібен у кожному запиті редагування профілю.

**Наслідки:** e2e-хелпер `completeTestProfile` тепер ставить і `elo` (з NTRP), бо інакше CHECK
відкидає профіль; сід оновлено.

## 2026-10-12 — Ранжування стрічки за близькістю ELO (задача 3.8)

**Як зроблено:** `rankByEloCloseness()` у `lib/matching/elo-rank.ts` — чиста функція, сортує
офертоподібні об'єкти (`{ elo, startsAt }`) за `|elo офери − elo глядача|`, зростаюче; за рівної
відстані — за `startsAt`, найраніша перша.

**Чому так:**
- **Відсутній ELO (з будь-якого боку) = `Infinity`**, а не виняток чи пропуск рядка: оферта без
  ELO автора чи глядач без ELO просто не мають «відстані» для порівняння, тож потрапляють у кінець
  і там сортуються між собою за датою. Так одна функція без спеціального коду для гостя одразу
  покриває і «гість бачить стрічку за датою» (3.9): коли `viewerElo = null`, усі відстані рівні
  `Infinity`, і сортування фактично лишається лише за `startsAt`.
- **`Infinity − Infinity = NaN`**, а не `0` — перший варіант реалізації віднімав відстані напряму
  і `NaN` як результат компаратора ламав сортування (масив лишався в вихідному порядку,
  непередбачувано). Виправлено порівнянням відстаней на рівність перед відніманням; тест «сортує
  лише за датою, коли в глядача немає ELO» це закріплює.
- **Без прив'язки до `FeedOffer` чи Prisma:** функція не знає про стрічку чи БД, лише про форму
  `{ elo, startsAt }` — підключення до `/offers` і вибір поля ELO автора — задача 3.9.

**Наслідки:** 3.9 підключає цю функцію до `getOfferFeed()` (3.6): для залогіненого — виклик з його
`elo`, для гостя — з `null` (що дає сортування за датою, як і раніше).

## 2026-10-12 — Ранжування підключено до стрічки (задача 3.9)

**Як зроблено:** `getOfferFeed()` (`lib/offers/feed.ts`) приймає `viewerId: string | null`.
Якщо він є — запит виключає оферти цього автора (`feedWhere(..., viewerId)`, нова умова
`authorId: { not }`) і читає його `elo` окремим `db.user.findUnique`. Усі оферти, що лишились
після фільтрів 3.7, ранжує `rankByEloCloseness()` (3.8) за `elo` глядача (або `null` для гостя —
сортування лишається за датою, як до 3.9), і лише тоді сторінка нарізається (`?page=`).
`app/offers/page.tsx` передає `viewer?.id ?? null` з `getCurrentUser()`.

**Чому так:**
- **Пагінація тепер рахується в пам'яті, не в БД** (`skip`/`take` прибрано, запит читає все, що
  підходить під фільтри): правильний «Best match» на сторінці 2 залежить від порядку всього
  відфільтрованого списку, а не лише 20 рядків, які мала б повернути стара пагінація із
  зсувом. Рахунок за ELO в самому SQL (`ORDER BY abs(elo - :viewer)`) означав би raw-запит і
  ризик розійтися з `rankByEloCloseness`; для розміру стрічки одного міста (запис 3.6: той
  самий здогад, що для неперейнятого списку клубів, 2.5) читати все і сортувати в JS — простіше й
  безпечніше. Якщо стрічка виросте, це перший кандидат на повернення до SQL-пагінації з
  обчисленим стовпцем.
- **Власні оферти виключає сам запит (`WHERE`), а не фільтр після ранжування:** вони не мають
  сенсу як «збіг» (відстань до себе — завжди 0, тож вони б завжди ранжувались першими), і
  видимість не має залежати від сортування, що саме активне.
- **`elo` автора читається в запиті лише для ранжування й одразу відкидається** — `FeedOffer`
  не набув нового поля; той самий прийом, що й у `_count`.

**Наслідки (торкнуті e2e, рев'ю варто переглянути):**
- E2E 3.6/3.7/3.5 раніше перевіряли свіжостворену оферту в стрічці, залишаючись залогіненими як
  автор — тепер це показало б порожньо. Виправлено додаванням `page.context().clearCookies()`
  перед переглядом стрічки (`e2e/offers-feed.spec.ts`, `e2e/offer-create.spec.ts`) — той самий
  прийом, що вже був у `e2e/offer-page.spec.ts` для гостя. Новий e2e-тест у `offers-feed.spec.ts`
  перевіряє саме виключення: залогінений не бачить власної оферти, бачить чужу.
- Афектовані e2e (`offers-feed`, `offer-create`, `offer-page`) прогнано локально через
  scratchpad-конфіг (channel `msedge`), `--workers=1` — усі пройшли.

**Перша міграція проєкту, що відкриває читання `public` для `authenticated` — потребує

- **Задача 1.17 виявилась уже зробленою** (міграції від 2026-09-29 плюс `e2e/rls.spec.ts` від

## 2026-10-14 — Формула ELO

**Рішення:** очікуваний результат `E = 1 / (1 + 10^((Rb − Ra) / 400))`; враховується лише
перемога/поразка (рахунок на ELO не впливає); `K = 40` для перших 10 підтверджених матчів
гравця, далі `K = 20`; кожен гравець рахує свій K окремо; результат округлюється (`Math.round`);
нижня межа рейтингу — 100.
**Чому:** стандартна формула ELO зі змінним K — вищий K для нових гравців дає рейтингу швидше
знайти правильний рівень, поки історії матчів ще мало.
**Наслідки:** закриває 4.3 (слайс E). Стартовий ELO з NTRP (задача 4.1) — окремий запис
2026-10-11, цей запис стосується лише перерахунку за результатами матчів.

## 2026-10-15 — Системні повідомлення: `type` і nullable `sender_id` (задачі 3.16–3.18)

Доповнює модель 3.15.

**Рішення:** `Message` отримав `type` (enum `MessageType`: `TEXT` / `SYSTEM`, дефолт `TEXT`), а
`sender_id` став nullable — міграція `20261015090000_add_message_type` (застосована напряму, тим
самим обхідним шляхом, що й 3.22, — `auth.uid()` з 3.15 і далі ламає `migrate dev`). CHECK
`(type = 'SYSTEM') = (sender_id IS NULL)` тримає їх разом: системне повідомлення — завжди без
відправника, текстове — завжди з ним. `postSystemMessage(thread, text)` (`lib/messages/`) пише такий
рядок за `{ offerJoinId }` чи `{ offerId }` — той самий «рівно один тред» формат, що й у 3.15.
RLS-політика `SELECT` із 3.15 перевіряє лише `offer_join_id`/`offer_id`, тож нового її виду це не
торкається — системні повідомлення видимі тим самим учасникам треду, без нової політики.

Та ж міграція додає `messages` у публікацію `supabase_realtime` (`ALTER PUBLICATION … ADD TABLE`),
порожню досі (перевірено `pg_publication_tables` на dev-БД перед зміною) — без цього Realtime
(3.18) не віддав би жодного INSERT, незалежно від RLS. Це не нова точка доступу: публікація лише
вирішує, для яких таблиць Postgres надсилає `postgres_changes` далі, а яким рядкам серед них бути
видно — і далі вирішує RLS (3.15), на рівні підключення підписника. Тому це не підпадає під умову
зупинки «нова RLS-політика, що відкриває читання» (AGENTS.md §10) — жодна політика не змінилась.

**Чому так:**
- Nullable, а не окрема таблиця для системних повідомлень: той самий тред, та сама історія, той
  самий порядок за часом — окрема таблиця змусила б UI (3.17) об'єднувати два джерела й сортувати
  вручну, заради одного nullable стовпця.
- CHECK, а не лише конвенція в коді: `postSystemMessage` і `sendMessage` — єдині місця запису
  (власник таблиці, RLS не діє), але CHECK гарантує те саме навіть для рядка, вставленого не через
  них (SQL-редактор, майбутній код), так само, як CHECK на `messages_one_thread_check` у 3.15.
- `postSystemMessage` приймає `{ offerJoinId } | { offerId }`, хоча сьогодні викликається лише з
  `{ offerJoinId }`: груповий тред (3.21) і майбутні системні підказки (сесії 04, 06, 07) — той
  самий виклик, без нової функції.

**Перевірено:** `pnpm build/lint/typecheck/test` зелені (403 тести). `e2e/offer-page.spec.ts`
(флоу №3, частина 2) — вітальне повідомлення, обмін повідомленнями автор↔гравець, повідомлення зі
`<script>` показане як текст, третя людина не бачить треду; `e2e/messages-rls.spec.ts` (RLS,
незмінений) — усе ще зелено (msedge, `--workers=1`, кожен файл окремо один раз). Повний прогін
e2e один раз упав на лімітах magic-link Supabase Auth (запис 2026-10-11/2026-10-14) — ті самі
симптоми (`/login?error=link`, `AuthApiError: Request rate limit reached`) на файлах, що щойно
пройшли окремо, включно з обома зачепленими цією сесією; не регресія.

**Наслідки:** 3.21 (груповий тред) перевикористовує UI (`components/message-thread.tsx`,
`components/join-thread.tsx`) і `postSystemMessage({ offerId })` без змін до RLS чи моделі.

Деталізує рішення «Rate limiting без нового сервісу» від 2026-10-14.

**Рішення:** `checkRateLimit(subject, action, now?)` (`lib/rate-limit/check-rate-limit.ts`) —
фіксоване вікно (не ковзне): `windowStart = floor(now / windowMs) * windowMs`, один upsert-рядок
`RateLimitCounter` на `(subject, action, windowStart)`, лічильник інкрементується і порівнюється
з лімітом тим самим запитом. `subject` — `userId` для всіх дій, крім `MAGIC_LINK`, де це email
(сесії ще немає на цьому кроці). Вікна: добові (UTC, не варшавська календарна доба) для
`NEW_OFFER`/`JOIN_REQUEST`/`REPORT`, 10 хв для `MESSAGE`, година для `MAGIC_LINK` — значення з
таблиці рішень 2026-10-14. «5 активних оферт» (6.17) — окрема пряма перевірка кількості
(`lib/offers/active-offers.ts`), не підпадає під `checkRateLimit`: це не вікно часу, а «скільки
зараз одночасно», тому рахується `db.sparringOffer.count()` напряму.
**Чому:**
- Фіксоване, а не ковзне: ковзне вікно без нового сервісу означало б журнал окремих подій і
  підрахунок рядків у діапазоні на кожну перевірку — дорожче й складніше заради точності, яка не
  потрібна для анти-зловживання (на відміну від білінгу). Ціна фіксованого вікна — сплеск до
  вдвічі ліміту на межі вікна — прийнятна при лімітах, які з запасом перевищують нормальне
  використання (перевірено: жоден існуючий e2e-флоу не наближається до жодного ліміту).
- UTC-доба, не варшавська: на відміну від `offerPushSentOn` (лічильник пушів 5.16, що навмисно
  скидається о варшавській півночі заради UX), тут межа доби не видима користувачу — вона лише
  захищає від зловживання, тож простіша UTC-арифметика без часового поясу достатня.
- `subject` рядком, не UUID-зв'язком із `User`: `MAGIC_LINK` перевіряється до того, як існує
  сесія чи навіть рядок `users` (вхід новою поштою) — лічильник мусить пережити відсутність
  користувача.
**Наслідки:** закриває 6.16-6.18 (слайс I). Підключено до `createOffer`, `requestToJoin`,
`sendMessage`, `createReport` (3.19) і `sendMagicLink` — новий виклик `checkRateLimit` перед
Supabase, що й так має власний 429 (не видалено, лишається другим рубежем).

## 2026-10-15 — Польська мова: `next-intl`, без префікса в URL, локаль у cookie (задача 1.20)

Реалізує рішення від 2026-10-14 (англійська + польська до запуску; `next-intl`; українська —
після запуску).

**Рішення:**
- Бібліотека — `next-intl` (нова залежність, `4.14.9`, зафіксована точно, як решта прямих
  залежностей у `package.json`). Без `[locale]`-сегмента в маршрутах: next-intl підключений у
  «cookie-only» режимі (`i18n/request.ts` читає cookie напряму, без `createMiddleware`/
  `localePrefix`), не бібліотечний роутинг.
- Визначення мови: `proxy.ts` (вже існуючий єдиний проксі) на кожен запит без cookie
  `NEXT_LOCALE` парсить заголовок `Accept-Language` (перша мова з підтримуваних — `pl` чи `en`,
  інакше `en`) і пише cookie на рік. Із cookie — завжди вона, без повторного парсингу заголовка.
  `getRequestConfig` (`i18n/request.ts`) читає тільки cookie, із тим самим дефолтом `en`, якщо
  вона все ж відсутня (прямий виклик без проксі, напр. в тесті).
- Перемикач мови (футер, профіль) — клієнтський компонент, що ставить cookie й викликає
  `router.refresh()`; на профілі додатково зберігає вибір у `users.locale` (нова колонка,
  `Locale` enum `EN`/`PL`, дефолт `EN`) серверною дією. Це поле читає лише розсилка (листи,
  push) — вибір мови для самого рендеру сторінки завжди з cookie, не з БД, щоб не додавати запит
  до бази на кожен запит заради того, що cookie вже дає.
- Дати й час: `formatKrakowTime` (було — захардкоджений `Intl.DateTimeFormat("en-GB", …)`)
  замінено на `next-intl`'s `useFormatter`/`getFormatter` з `timeZone: "Europe/Warsaw"` і мовою
  запиту — та сама з точністю до часового пояса дата читається по-англійськи чи по-польськи
  залежно від вибраної мови, а не завжди по-британськи.
- Zod-повідомлення: кожна user-facing схема (`profile`, `login`, `offer`, `match-result`,
  `message`, `report`) стала функцією `xSchema(t)`, що приймає вже готову функцію перекладу
  (`useTranslations`/`getTranslations` з простору `Validation.<schema>`) і будує схему з
  перекладеними повідомленнями. `club.ts` (лише `clubs:load`, не користувацький UI) і
  `push-subscription.ts` (повідомлення нікому не показуються, лише внутрішня перевірка) —
  без змін, не користувацькі рядки.
**Чому:**
- Без префікса — явне рішення 2026-10-14 (менше змін у маршрутах, SEO-URL після запуску), тому
  next-intl у «cookie-only» режимі, не в режимі `[locale]`-сегмента, який цей проєкт і так не
  хотів.
- cookie, не БД, для самого рендеру — та сама логіка, що вже обрана для `offerPushSentOn` і
  рейт-лімітів: уникати зайвого запиту на кожен рендер, коли простіший механізм (тут — cookie)
  дає те саме. БД-поле існує лише тому, що розсилка (cron, без поточного запиту й його cookie)
  не має іншого способу знати мову користувача.
- Схема `xSchema(t)` замість глобального Zod error map: повідомлення тут — специфічні для поля
  (`"Enter your email address."`, не загальне `invalid_type`), а Zod-овий вбудований i18n
  (`zod/v4/locales`) перекладає лише стандартні повідомлення типу, не ці.
**Наслідки:** міграція `20261015150000_add_user_locale` (застосована напряму — той самий
обхідний шлях через shadow-БД і `auth.uid()`, що кожна міграція з 3.15) додає `users.locale`.
Перевірка захардкоджених рядків (скрипт, DoD 1.20) падає на будь-якому текстовому літералі в
JSX усередині `app/` і `components/`, крім явного списку винятків (атрибути, що не є текстом
для гравця: `className`, `href`, `data-*`, значення `<option value>` тощо, перелічені в самому
скрипті).
