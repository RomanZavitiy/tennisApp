# decisions.md — журнал архітектурних рішень

Короткі датовані записи про реальні рішення (AGENTS.md §10): що вирішили і чому. Записи не
видаляються й не переписуються — якщо рішення змінюється, додається новий запис, який посилається
на старий. Нові записи — внизу.

Формат: `## YYYY-MM-DD — назва` · **Рішення** · **Чому** · (опційно) **Наслідки / посилання**.

## 2026-09-20 — MVP без системи бронювання кортів

**Рішення:** у MVP немає бронювання й оплати кортів. Сторінка клубу лише дає зовнішнє посилання
на бронювання в самого клубу.
**Чому:** головна цінність продукту — знайти партнера (matchFinder), а не замінити системи
бронювання клубів. Бронювання й платежі — великий окремий шмат роботи (інтеграції з клубами,
платіжний провайдер, повернення коштів), який відклав би запуск.
**Наслідки:** може бути переглянуто після MVP (Open Questions у плані).

## 2026-09-20 — Стек проєкту

**Рішення:** Next.js 15 (App Router) + TypeScript · Supabase (Postgres, Auth, Storage, Realtime) ·
Prisma · Tailwind CSS + shadcn/ui · react-leaflet + OpenStreetMap · React Hook Form + Zod ·
Resend · Vercel · GitHub Actions · Vitest + Playwright · pnpm.
**Чому:** один фреймворк для фронтенду й бекенду (без окремого API-сервера); один керований
сервіс замість окремих БД/auth/сховища/realtime; безкоштовні плани достатні на старті;
OpenStreetMap — без ключів і лімітів Google Maps; Zod-схема спільна для форми й сервера.
**Наслідки:** будь-яка бібліотека чи сервіс поза цим списком — лише після погодження з людиною
(AGENTS.md §2). Точні версії Next.js / Node / Prisma — окремим записом (задача 0.3).

**Рішення:** обидва способи через Supabase Auth; паролів немає.
**Чому:** без паролів — немає скидання пароля і зберігання хешів; Google — найшвидший вхід для

## 2026-09-24 — Формат оферти

**Рішення:** синґл за замовчуванням, парна гра — опційно. У парній оферті автор може позначити
«вже маю партнера»: тоді потрібно 2 гравці, інакше 3. Партнер у MVP — лише позначка, не
прив'язаний акаунт.
**Чому:** синґл — основний сценарій спарингу; парна гра потрібна частині гравців, але прив'язка
партнера-акаунта ускладнює модель без великої користі на старті. Формула — у задачі 3.1.

## 2026-09-24 — Чат

**Рішення:** окремий приватний тред на кожну заявку (автор ↔ гравець); у парній грі прийняті
учасники додатково мають спільний груповий тред.
**Чому:** приватний тред дозволяє домовитись до прийняття без розкриття телефону/email; груповий
потрібен, щоб четверо людей узгодили гру в одному місці.

## 2026-09-24 — ELO лише для синґлів

**Рішення:** рейтинг рахується лише за синґли; результати парних ігор у MVP не вносяться.
**Чому:** ELO для пар потребує окремої моделі (рейтинг пари vs індивідуальний) — це ускладнення
без чіткої користі для MVP.

## 2026-09-25 — Версії Next.js, Node і Prisma (задача 0.3)

**Рішення:** Next.js **16** (на момент рішення 16.3.x) · Node **24 LTS** (24.x) · Prisma **7**

- Prisma: npm-тег `latest` на момент рішення вказує на `8.0.0-rc` — реліз-кандидат у фундамент

**Наслідки:** AGENTS.md §2 і README оновлено на Next.js 16. Точне закріплення версії Node і
pnpm у репо — задача 0.5; Prisma ставиться з явною версією (`prisma@7`), не `@latest`.
Локально потрібно оновити Node з 20 до 24 до початку 0.4.

## 2026-09-26 — Як закріплено Node і pnpm (задача 0.5)

**Рішення:** Node — `.nvmrc` (`24`) + `engines.node: ">=24 <25"` у `package.json` +
`engineStrict: true` у `pnpm-workspace.yaml`. pnpm — поле `packageManager: "pnpm@12.6.0"`.
`@types/node` піднято з `^20` до `^24`, щоб типи відповідали реальному рантайму.
**Чому:**
- Без `engineStrict` pnpm на невідповідному Node не показує навіть попередження — перевірено.
  З ним `pnpm install` падає з `ERR_PNPM_UNSUPPORTED_ENGINE`.
- `.nvmrc` читають nvm і `actions/setup-node` (CI, задача 0.16); `engines.node` читає Vercel, щоб
  обрати версію Node для білду.
- Інша версія pnpm не падає, а сама перемикається на версію з `packageManager` (перевірено з
  pnpm 10). Це сильніше за попередження: встановлення завжди йде тією самою версією.
- Верхня межа `<25` — щоб перехід на наступну major Node був свідомим рішенням, а не випадковістю.

## 2026-09-26 — Prettier: стандартні налаштування, без markdown, LF скрізь (задача 0.7)

**Рішення:** Prettier із налаштуваннями за замовчуванням (`.prettierrc.json` = `{}`);
`*.md` і `pnpm-lock.yaml` у `.prettierignore`; `.gitattributes` з `* text=auto eol=lf`.
**Чому:**
- Налаштування за замовчуванням — менше рішень і суперечок; код, згенерований create-next-app,
  їм уже відповідав.
- На документах Prettier переписує відступи в списках задач і розтягує таблиці: `docs/PLANNING.md`
  отримав би дифф на ~600 рядків без жодної користі. Документи пише людина — форматуємо їх руками.
- На Windows з `core.autocrlf=true` git віддає файли з CRLF, а Prettier очікує LF — локально
  `format:check` падав би на кожному файлі, а в CI (Linux) проходив би. `eol=lf` робить робочу
  копію однаковою на всіх машинах.

## 2026-09-26 — ESLint: strictTypeChecked + заборона console.log (задача 0.8)

**Рішення:** для `.ts/.tsx` увімкнено `typescript-eslint` `strictTypeChecked` (type-aware правила
через `projectService`); у `app/`, `lib/`, `components/` — `no-console` з дозволом лише на
`console.warn` і `console.error`. `typescript-eslint` додано прямою devDependency тієї ж версії,
що й у `eslint-config-next`.
**Чому:**
- `strictTypeChecked`, а не `recommendedTypeChecked`: код поки майже порожній, тож найсуворіший
  набір нічого не коштує зараз, а послабити окреме правило пізніше легше, ніж посилювати на
  готовому коді. Type-aware правила ловлять те, що людина на рев'ю легко пропустить
  (незачекані проміси, `any`, що «протікає» в типізований код).
- `console.warn/error` дозволені — це справжня діагностика (Epic 6 підключить моніторинг помилок);
  заборонено лише налагоджувальний `console.log`.
- Та сама версія `typescript-eslint` — інакше в ESLint потрапляють дві копії плагіна
  `@typescript-eslint`, і flat config падає з конфліктом плагінів.

## 2026-09-26 — Pre-commit хук: husky + lint-staged (задача 0.9)

**Рішення:** husky запускає lint-staged перед кожним комітом; для змінених `.ts/.tsx/.js/.mjs` —
`eslint --fix` і `prettier --write`, для `.json/.css/.yaml` — лише `prettier --write`.
Хук ставиться сам через скрипт `prepare` під час `pnpm install`. lint-staged — 17.5.1, не
найновіша 17.6.0.
**Чому:**
- Перевіряються лише файли в коміті — хук лишається швидким, коли проєкт виросте.
- Автовиправлення (`--fix`, `--write`) прибирає дрібниці без участі людини; справжні помилки
  (як-от `console.log`) не виправляються автоматично й блокують коміт.
- `typecheck` у хук не додано: `tsc` перевіряє весь проєкт і з ростом коду сповільнить кожен
  коміт; типи перевіряє CI (задача 0.16).
- 17.6.0 вийшла в день задачі, і pnpm відхилив її правилом `minimumReleaseAge` (захист від
  щойно опублікованих, можливо скомпрометованих версій), автоматично додавши виняток у
  `pnpm-workspace.yaml`. Виняток прибрано, взято попередню версію — правило не обходимо.

## 2026-09-28 — Як підключено Prisma 7 (задача 0.11)

**Рішення:** Prisma **7.10.0** (`prisma`, `@prisma/client`) плюс `@prisma/adapter-pg`. Клієнт
генерується в `lib/generated/prisma` (у `.gitignore`, перегенеровується в `postinstall`) і
створюється лише в `lib/db.ts`. CLI (міграції, studio) ходить через `DIRECT_URL`, а застосунок —
через `DATABASE_URL` (transaction pooler). `prisma.config.ts` читає `.env.local` вбудованим
`process.loadEnvFile` з Node. У `pnpm-workspace.yaml` дозволено install-скрипти `prisma`
(перевірка версії Node) і `@prisma/engines` (завантажує schema engine для міграцій).
**Чому:**
- У Prisma 7 клієнт працює лише через driver adapter; `@prisma/adapter-pg` — офіційний адаптер
  Prisma для Postgres, а не окрема бібліотека поза стеком.
- Prisma 7 сама не читає env-файли. Наші секрети лежать у `.env.local`, тому `.env` не заводимо,
  а замість `dotenv` беремо вбудований у Node 24 завантажувач: на одну залежність менше.
- `prisma init` не запускали: крім конфігу, він кладе свої skill-файли в `.agents/`, `.claude/`
  і `.windsurf/`, що змішалося б з нашими документами. Ті самі файли написано вручну.
- Клієнт тримаємо на `globalThis` у dev: перевірено 8 hot reload у `pnpm dev`, кількість
  з'єднань до бази лишалась 3.

## 2026-09-28 — Базова схема БД: конвенції та правила видалення (задача 0.12)

**Рішення:** каркас п'яти моделей — лише ключі, зв'язки, статуси й часові мітки; предметні поля
додають задачі 1.10, 2.1, 3.2, 3.10, 4.4. Конвенції:
- Таблиці, колонки й enum-и в Postgres — `snake_case` (`@@map`/`@map`), моделі в коді — як
  звично в Prisma (`SparringOffer`, `authorId`).
- Id — UUID, які генерує Postgres (`gen_random_uuid()`); `User.id` — це id з `auth.users` без
  зовнішнього ключа на нього. `created_at`/`updated_at` — `timestamptz` зі значенням за
  замовчуванням у БД.
- Статуси: оферта `OPEN / FULL / CANCELLED`, заявка `REQUESTED / ACCEPTED / DECLINED / WITHDRAWN`,
  результат `PENDING / CONFIRMED / DISPUTED`. Заявка унікальна для пари (оферта, гравець);
  результат — один на заявку.
- Видалення: користувач → його оферти й заявки (Cascade); оферта → її заявки (Cascade); клуб з
  офертами видалити не можна (Restrict); заявку з результатом матчу видалити не можна (Restrict).

**Чому:**
- `snake_case`: RLS-політики (1.17) і запити в SQL-редакторі Supabase пишемо руками — без лапок
  навколо кожної назви їх легше читати й менше помилок.
- UUID замість послідовних чисел: id видно в URL (`/players/[id]`, `/offers/[id]`), і за ними не
  можна перебрати всіх гравців. Значення за замовчуванням у БД — щоб рядки, вставлені не через
  Prisma (SQL-редактор, сід), теж отримували id і дати.
- Зовнішнього ключа на `auth.users` немає: Prisma керує лише схемою `public`, а підтримка кількох
  схем ускладнила б міграції. Зв'язок гарантує код (1.9), видалення акаунта — задача 6.15.
- `timestamptz`: зберігаємо UTC, показуємо в Europe/Warsaw — без плутанини з літнім часом.
- Статусу «прострочено» немає: минулі оферти ховаються за часом початку (3.20), а не фоновою
  задачею.
- Restrict на результатах: результати — історія ELO. Поки 6.15 не вирішила, що з ними робити
  (анонімізувати чи видаляти), видалення користувача, в якого є будь-який внесений результат, блокує БД,
  а не тихо стирає рейтинг суперників.
**Наслідки:** Postgres не створює індекс на зовнішній ключ сам — кожен FK покритий індексом
(окремим або унікальним). Таблиці в БД з'являться лише з першою міграцією (0.13).

## 2026-09-29 — RLS увімкнено на всіх таблицях, без політик (до задачі 1.2)

**Рішення:** окремі міграції після `init` вмикають Row Level Security на всіх п'яти таблицях і на
службовій `_prisma_migrations` без жодної політики, тобто «deny by default». Точкові політики
(Storage, Realtime) і повний ADR — у задачах 1.2 і 1.17.
**Чому:** Supabase автоматично відкриває схему `public` через Data API. Без RLS будь-хто з
публічним anon-ключем міг би читати й змінювати таблиці напряму, минаючи server actions і
перевірки в коді. Prisma підключається як `postgres`, власник таблиць, і на неї RLS не діє,
тож застосунок працює як раніше (перевірено: `anon` бачить 0 рядків, власник — усі).
**Наслідки:** кожна нова міграція, що створює таблицю, має в тому ж файлі вмикати для неї RLS:
Prisma не знає про RLS і сама цього не додасть. Команду для `_prisma_migrations` загорнуто в
перевірку існування таблиці, бо тіньова БД `migrate dev` проганяє міграції без неї.

## 2026-09-29 — Сід на чистому SQL (задача 0.14)

**Рішення:** сід — файл `prisma/seed.sql`, який `pnpm prisma db seed` запускає через
`prisma db execute`. Кожен рядок має фіксований id; `ON CONFLICT` повертає наявний рядок до
сідового статусу, а не додає копію. Клуби сід не створює — їх заповнює Epic 2.
**Чому:** сід на TypeScript потребує окремого запускача (`tsx`), бо Node не може виконати
згенерований Prisma Client напряму: у ньому імпорти без розширень. SQL-сід обходиться без
нової залежності, а назви в БД і так `snake_case`, зручні для ручного SQL (див. запис 0.12).

## 2026-10-03 — Спосіб входу і e2e-вхід без пошти (задача 1.1)

Деталізує запис «Вхід: magic link + Google OAuth» від 2026-09-24.

**Рішення:**
- Вхід лише через Supabase Auth: magic link на email і Google OAuth. Паролів немає —
  провайдер Email/Password для паролів не вмикаємо.
- Обидва способи повертаються в один роут `/auth/callback`, який створює сесію в cookie:
  для Google він обмінює `code` на сесію, для magic link перевіряє `token_hash` + `type`. Лист
  веде на callback з `token_hash`, а не з PKCE-кодом: PKCE-код спрацьовує лише в тому браузері,
  де ввели email, а лист часто відкривають на телефоні. Шаблон листа в Supabase змінює власник
  у задачі 1.6.
- Адресу повернення застосунок бере з origin поточного запиту, тож вхід на preview-деплої
  повертає на той самий preview, а не на production. Supabase пропускає лише адреси зі списку
  Redirect URLs: `https://spinbuddy.vercel.app/**`, `https://spinbuddy-*.vercel.app/**`,
  `http://localhost:3000/**` (`pnpm dev`) і `http://localhost:3100/**` (Playwright). Site URL —
  production.
- Один email — один акаунт: Supabase автоматично зв'язує Google-ідентичність з наявним
  користувачем, якщо email збігається і підтверджений (Google віддає лише підтверджені). Окремого
  коду для злиття акаунтів не пишемо — це перевіряє DoD задачі 1.7.
- **E2E без пошти (задача 1.18):** Playwright перед тестом створює користувача через admin API
  Supabase (`auth.admin.createUser` з `email_confirm: true`) і отримує для нього magic link через
  `auth.admin.generateLink` — цей виклик лист не надсилає, а повертає `hashed_token`. Тест
  відкриває `/auth/callback?token_hash=…&type=magiclink`, тобто проходить той самий callback, що й
  реальний користувач. Після прогону тестові користувачі видаляються (`auth.admin.deleteUser`); їх
  email має впізнаваний вигляд (`e2e-<uuid>@example.com`), щоб залишки після обірваного прогону
  можна було знайти й прибрати.
- Admin API потребує `SUPABASE_SECRET_KEY`. Його читає лише код Playwright у `e2e/`; застосунок
  його не імпортує, у Vercel його немає. Локально він лежить у `.env.local`, для e2e у CI — у
  GitHub Actions secrets (коли e2e потрапить у CI).

**Чому:**
- Без паролів немає скидання пароля, зберігання хешів і перебору паролів; magic link + Google
  покривають усіх користувачів.
- Один callback — одне місце, де створюється сесія і (з 1.9) рядок `User`, незалежно від способу
  входу.
- Відкинуті варіанти e2e-входу: пароль для тестового користувача — довелося б увімкнути вхід за
  паролем і в production; читання пошти (Inbucket/Mailpit) — є лише в локальному Supabase, а ми
  працюємо з хмарним; запис cookie сесії напряму — формат cookie внутрішній для бібліотеки
  Supabase, і тест минав би callback, який якраз треба перевіряти. `generateLink` не витрачає
  ліміт вбудованого SMTP (кілька листів на годину до задачі 1.19).

**Наслідки:** preview і production поки ділять один проєкт Supabase (запис про 0.18), тож
тестові користувачі з'являються в тому самому `auth.users`, що й справжні, — прибирання після
прогону обов'язкове, а не «бажане». Redirect URLs і шаблон листа живуть у дашборді Supabase, не в
git; якщо зміниться домен (5.13) чи порт, їх треба оновити вручну.

## 2026-10-03 — Стратегія RLS разом із Prisma (задача 1.2)

Продовжує запис «RLS увімкнено на всіх таблицях, без політик» від 2026-09-29.

**Рішення:**
- Усі читання й записи даних застосунку — на сервері через Prisma: Server Components читають,
  server actions змінюють. Браузер не ходить у таблиці `public` напряму через supabase-js (ні
  publishable-ключем, ні з сесією користувача).
- RLS у `public` — «deny by default» для ролей `anon` і `authenticated`: RLS увімкнено на кожній
  таблиці, політик немає. Таблиця без політики — норма, а не недогляд.
- Точкові політики з'являються лише там, де браузер справді говорить із Supabase сам:
  - **Storage** (задача 1.13): bucket `avatars`. Читання публічне; писати, замінювати й видаляти
    файли користувач `authenticated` може лише у своїй папці — перший сегмент шляху дорівнює
    `auth.uid()`. Файл браузер вантажить у Storage напряму, а шлях до нього в `User` записує
    server action, перевіривши, що шлях починається з id цього користувача.
  - **Realtime** (задачі 3.15–3.18): якщо чат слухатиме зміни таблиці, потрібна політика
    `SELECT` для `authenticated` лише на таблиці повідомлень і лише для учасників треду. Writes
    і там ідуть через server action. Конкретний вигляд політики — рішення 3.15.
- Кожна нова таблиця вмикає RLS у тій самій міграції (правило з запису 2026-09-29 лишається).
  Нова політика на таблиці `public` — лише окремою міграцією з поясненням у `decisions.md`.

**Де діє RLS, а де авторизацію робить код:**

| Шлях до даних | Роль у Postgres | Хто перевіряє доступ |
| --- | --- | --- |
| Prisma (Server Components, server actions) | `postgres`, власник таблиць — RLS не діє | код: `requireUser()` (1.5) і умова власника в запиті |
| supabase-js з publishable-ключем, без сесії | `anon` | RLS: у `public` — нічого |
| supabase-js із сесією користувача | `authenticated` | RLS: у `public` — нічого; Storage/Realtime — політики вище |
| supabase-js із `SUPABASE_SECRET_KEY` | `service_role` — RLS не діє | лише e2e-хелпер (1.18), застосунок цей ключ не має |

Звідси правила для коду, бо RLS тут не підстрахує:
- Кожна server action спершу викликає `requireUser()`: middleware (1.4) server actions не
  захищає.
- Зміна чужого рядка відсікається в самому запиті — `where` містить і `id`, і власника
  (`authorId: user.id`), а не лише `id` з форми.
- Приватні поля (дата народження з 1.10) не потрапляють на публічні сторінки: запити для чужого
  профілю роблять явний `select` потрібних полів, а не віддають рядок `User` цілком. RLS діє на
  рядки, не на колонки, і на Prisma не діє зовсім.

**Чому:**
- Prisma підключається як власник таблиць, тож політики RLS на неї не впливають. Якби доступ
  описували політиками, правила жили б у двох місцях (SQL-політики і код), а перевіряла б їх
  лише половина запитів. Один шлях до даних — одне місце, де читати й тестувати авторизацію.
- Supabase відкриває `public` через Data API кожному з publishable-ключем, який вшитий у
  клієнтський бандл. «Deny by default» закриває цей шлях повністю, навіть якщо в коді колись
  з'явиться помилка.
- Storage і Realtime працюють лише через Supabase-клієнт і перевіряють доступ лише політиками —
  обійти їх через Prisma неможливо, тому там політики обов'язкові. Пряме завантаження в Storage
  ще й обходить ліміт тіла запиту функцій Vercel (4,5 MB), менший за ліміт фото.

**Наслідки:**
- Задача 1.17 зводиться до перевірки: RLS уже ввімкнено міграціями від 2026-09-29, лишається
  скрипт або тест, що anon- і authenticated-запити через supabase-js до кожної таблиці `public`
  повертають порожньо.
- Рев'ю кожної server action перевіряє `requireUser()` і умову власника — це головний механізм
  авторизації, а не другий рубіж.

  `lib/validation/`, і її перевіряють і форма в браузері, і server action. Форма має `noValidate`,
  щоб помилку показував Zod, а не вбудована валідація браузера.
- `/auth/callback` розбирає параметри через `parseCallbackParams()` (`lib/auth/callback.ts`):
  `code` — Google, `token_hash` + `type` (`email` / `magiclink` / `signup`) — magic link. Помилка
  Supabase, невідомий тип чи прострочене посилання → `/login?error=link` із повідомленням, а не
  500.
- Шаблони листів **Confirm signup** і **Magic Link** у Supabase (Authentication → Emails)
  посилаються на `{{ .RedirectTo }}&token_hash={{ .TokenHash }}&type=email`. `RedirectTo` —
  це `https://<поточний origin>/auth/callback?next=…`, який задає server action; він завжди
  містить `?`, тому далі йде `&`. Новому користувачу Supabase шле Confirm signup, наявному —
  Magic Link, тож міняються обидва.
**Чому:** без адаптера довелося б писати власний resolver для Zod — той самий код, лише наш.
Посилання з `token_hash` працює в будь-якому браузері (див. запис 1.1).
**Наслідки:** якщо origin деплою не входить у Redirect URLs, Supabase підставить Site URL без
`?next=…`, і посилання з листа зламається. Тому новий домен (5.13) спершу додається в Redirect
URLs. Шаблони живуть лише в дашборді Supabase.

## 2026-10-04 — Вихід лише на цьому пристрої; header читає сесію (задача 1.8)

**Рішення:** «Sign out» — server action `signOut()` (`app/auth/actions.ts`), що викликає

**Як це лягло в схему:** у `clubs` додано `slug` (унікальний), `name`, `address`, `district`,
`latitude`/`longitude` (`double precision`), `court_count`, `surfaces`, `indoor`, `verified_at`

**Чому так:**
- **Покриття масивом, «криті» окремо.** Клуб у Кракові часто має і мачку, і хард, а взимку
  накриває частину кортів балоном. Одне значення на клуб (`indoor-hard`) змішало б дві різні

  `surface` згодом візьме оферта (3.2), тож його визначено один раз тут.
- **`slug` — стабільний ключ для завантаження даних (2.3).** `id` генерує Postgres, у файлі
  `prisma/data/clubs.json` його немає, тож за ним не впізнати «той самий клуб» при повторному
  завантаженні. `slug` власник вписує у файл сам (`kks-nadwislan`); upsert за ним оновлює
  наявний рядок, і `id` — а з ним посилання `/clubs/[id]` і оферти, прив'язані до клубу, — не
  змінюється. Перейменування клубу — це зміна `name`, а не `slug`.
- **`verified_at` — дата, коли власник востаннє звірив дані з джерелом.** Ціни й телефони
  застарівають; сторінка клубу (2.8) покаже «Info checked on …», щоб гравець знав, наскільки
  свіжі дані, і перепитав у клубу, якщо вони давні. Тип `date`, бо перевірка — подія дня, а не
  моменту. Саме джерело (посилання, звідки взято дані) лишається у файлі даних (DoD 2.2) і в БД
  не потрібне — користувачам воно нічого не додає.
- **Координати — `double precision`, не PostGIS.** Для ~15 маркерів на карті просторові запити
  не потрібні; нова розширена залежність БД не виправдана.
- **CHECK-обмеження в міграції**, яких не виразити в `schema.prisma`: формат `slug`; назва й
  адреса не з самих пробілів; координати в межах Землі; кортів > 0; `surfaces` не NULL, не
  порожній і без NULL-елементів (Prisma робить колонку-масив nullable, тож обов'язковість
  тримає CHECK); `website_url` і `booking_url` починаються з `http://` або `https://` — сторінки

  Вужчі правила (координати в межах Кракова, без повторів у `surfaces`) — у Zod-схемі 2.3.
  Перевірено на dev-БД у транзакціях з відкатом: валідний рядок проходить, кожне з порушень
  відкидає свій CHECK, невідоме покриття — сам enum.

**Наслідки:** міграцію застосовано до dev-проєкту Supabase, спільного поки з preview і
production (запис про 0.18) — безпечно, бо зміни лише адитивні, а таблиця порожня. Нова таблиця
не з'явилась, тож RLS-тест (1.17) змін не потребує. `seed.sql` не змінюється: він клубів не
створює (запис про 0.14). Назви покриттів і `indoor` для показу додасть задача, що вперше їх
показує (2.8).

**Рішення власника:** додати dev-залежність `tsx` (4.23.15), щоб завантажувач клубів був на

**Чому так:**

- **Спершу весь файл, потім запис.** Схема перевіряє кожен запис і кидає одну помилку зі
  списком усіх поганих клубів за назвою (або номером, якщо назви немає), тож зламаний файл
  виправляють за один прохід, а до бази нічого не доходить. Повтор `slug` у файлі — теж помилка.
- **Правила лише в Zod:** координати в межах Кракова (прямокутник навколо міста з запасом),
  без повторів у `surfaces`, `verifiedAt` не в майбутньому (календар Кракова, як у профілі),
  `source` — обов'язкове http(s)-посилання (DoD 2.2). Схема строга: незнайомий ключ (`phnoe`)
  — помилка, а не тихо загублене поле. `source` і `todo` у БД не пишуться.
- **Клуби, яких немає у файлі, не видаляються.** На клуб можуть посилатися оферти
  (`onDelete: Restrict`), тож прибрати клуб — окремий свідомий крок.

**Перевірено:** на dev-БД у транзакції з відкатом: два запуски дають 20 рядків, а не 40;
`id` після повторного запуску той самий; змінені `courtCount` і `phone` оновлюються. Скрипт на
файлі з координатами поза Краковом падає з `Club "Błonia Sport" — latitude: Not in Kraków.` і
кодом 1.

**Наслідки:** клуби в базі з'являться лише після ручного запуску `pnpm clubs:load`. Поки
dev, preview і production ділять один проєкт Supabase (запис 0.18), це одразу й production —
а там зараз тестові дані з 2.2a (однаковий телефон, випадкові райони).

## 2026-10-07 — Карта клубів: Leaflet лише в браузері, явна іконка маркера (задача 2.4)

**Рішення:** додати `leaflet` (1.9.4) і `react-leaflet` (5.0.0) у `dependencies` та
`@types/leaflet` (1.9.22) у `devDependencies`. Обидві бібліотеки вже є в стеку AGENTS.md. Карта —
`components/club-map/`: `club-map.tsx` рендерить саму карту, `index.tsx` — обгортка, через яку її
імпортують сторінки. Центр — Rynek Główny, тайли `tile.openstreetmap.org` з атрибуцією
«© OpenStreetMap contributors» і посиланням на `openstreetmap.org/copyright`.

**Чому так:**
- **`@types/leaflet` потрібен.** У `leaflet` 1.9 немає власних типів, а `.d.ts` react-leaflet
  імпортують їх з `leaflet` — без пакета TS strict не збирається. Build-скриптів у цих пакетів
  немає, тож `allowBuilds` не змінювався.
- **SSR вимкнено через `next/dynamic(..., { ssr: false })` у клієнтській обгортці.** Leaflet
  звертається до `window` вже під час імпорту, тож модуль карти не можна навіть завантажувати на
  сервері. У Next 16 `ssr: false` дозволено лише в Client Components, тому `dynamic` живе в
  `index.tsx` з `"use client"`, а Server Components (2.6) імпортують тільки його і передають дані
  клубів пропсами. Поки модуль вантажиться, на місці карти — плейсхолдер тієї ж висоти.
- **Іконка маркера — явний `L.icon` з PNG у `public/leaflet/`.** Стандартна іконка Leaflet шукає
  картинки за шляхом з `leaflet.css`, а після бандлера цей шлях ламається. Глобальний хак
  (`delete L.Icon.Default.prototype._getIconUrl` + `mergeOptions`) чіпає приватний API, тому кожен
  маркер отримує свою іконку явно. Імпорт PNG з `leaflet/dist/images` не підійшов: Turbopack
  віддає для файлу з `node_modules` рядок-URL, а не `StaticImageData`, яку обіцяють типи Next, —
  `.src` у браузері був `undefined`, і сторінка падала з «iconUrl not set». Тож три PNG (разом
  ~4,5 КБ) скопійовано з `leaflet` 1.9.4; при оновленні Leaflet їх варто звірити.
- **`isolate` на контейнері карти.** Панелі й кнопки Leaflet мають z-index до 1000 і без
  окремого контексту накладання вилазили б поверх мобільного меню.

**Перевірено:** `pnpm build` без `window is not defined`; e2e `clubs-map.spec.ts` (карта, тайли
OSM, посилання атрибуції, жодної помилки в браузері); на production-збірці з тимчасовим маркером
іконка й тінь завантажуються (25×41 і 41 px), мобільне меню перекриває карту.

**Наслідки:** `/clubs` поки показує карту без маркерів; маркери клубів з попапом додасть 2.5.

## 2026-10-07 — Маркери клубів: дані з БД на кожен запит, e2e на тимчасовому клубі (задача 2.5)

**Як зроблено:** `/clubs` — Server Component, читає з `clubs` лише `id`, `name`, `address` і
координати та передає їх карті пропсами. Кожен маркер відкриває попап: назва, адреса, посилання
«Club details» на `/clubs/[id]` (саму сторінку додасть 2.8).

**Чому так:**
- **`await connection()` перед запитом.** Сторінка читає БД на кожен запит, а не під час
  `next build`: CI збирає без бази (`ci.yml`), а клуби, завантажені `pnpm clubs:load`, мають
  з'являтися без нового деплою.
- **`<div>`, а не `<p>`, у попапі.** `leaflet.css` дає абзацам у попапі великі відступи, а його
  правила поза `@layer` перемагають утиліти Tailwind.
- **e2e створює власний клуб.** Справжніх клубів у БД поки немає (дані збирає власник), і тест не
  має залежати від них. Тест додає клуб зі `slug` на `e2e-` через admin-клієнт і видаляє його
  у `finally`; `global-teardown.ts` прибирає такі клуби, старші за годину, якщо прогін обірвався
  — інакше вони стояли б на справжній карті.

**Наслідки:** доки `pnpm clubs:load` не запущено зі справжніми даними, карта на `/clubs` порожня.
DoD «15 маркерів на правильних місцях» перевіряється після завантаження даних.

## 2026-10-08 — Сторінка `/clubs`: список + карта, перемикач на мобільному (задача 2.6)

**Як зроблено:** сторінка (Server Component) читає клуби один раз і віддає ті самі дані списку
(`components/club-list.tsx`) і карті. Розкладку робить `components/clubs-view.tsx` — єдиний
клієнтський шматок: на десктопі (`lg`) список і карта поруч, на телефоні кнопки List/Map
показують щось одне. Список і карта приходять у нього слотами, тож список лишається серверним.

**Чому так:**
- **Перемикач — стан у клієнті, а не `?view=map` у URL.** Перемикання через URL щоразу
  повторювало б серверний рендер із запитом до БД заради показу іншої половини тих самих даних.
  Посилання на «карту одразу» поки нікому не потрібне.
- **Приховування через CSS, а не демонтаж.** Карта не перезавантажує тайли і не губить позицію,
  а список — прокрутку, коли телефон перемикається туди-назад. Розкладку обирає CSS-брейкпоінт,
  тож JS не мусить знати ширину екрана.
- **`ResizeObserver` → `invalidateSize()` у карті.** Leaflet міряє контейнер лише при монтуванні
  й після resize вікна. На телефоні карта монтується прихованою (0×0) і після показу малювала
  маркери не там — e2e без цього виправлення падає з зсувом маркера на 177 px.
- **Райони — підписи з `DISTRICT_LABELS`** (`lib/profile/options.ts`), тих самих, що в профілі.

**Наслідки:** e2e-файли `clubs-map` і `clubs-page` створюють тестові клуби паралельно, тому в
різних точках — інакше маркери перекривають один одного і клік влучає не в той. Синхронізація
списку з картою — 2.7, туди ж природно перейде стан вибраного клубу в `ClubsView`.

## 2026-10-09 — Схема клубу під реальні дані; тестового клубу в БД немає (задача 2.11)

**Рішення власника:** розширити схему під зібрані дані, а не підганяти дані під схему; тестовий
клуб у спільну БД не додавати.

**Як зроблено:** міграція `club_unknown_fields` лише додає: `indoor_courts` отримує `PARTIAL`
(частина кортів у залі цілий рік, решта відкриті), `surface` — `ARTIFICIAL_CLAY` (штучна мачка);
`district` і `indoor` можуть бути NULL; CHECK `clubs_surfaces_check` більше не вимагає
непорожнього списку (не NULL і без NULL-елементів — як і раніше). Дані власника перенесено в
`prisma/data/clubs.json` з перейменуванням `FULL` → `YEAR_ROUND`, `SEASONAL` → `WINTER_BUBBLE`.

**Чому так:**
- **NULL / порожній список = «невідомо», а не вигадане значення.** Як і з ціною (запис про
  `clubs_v2.json`): заглушка на сторінці виглядає як правдива інформація. Сторінки просто не
  показують порожнє поле.
- **Район NULL — для клубів за межею міста** (Кришпінів — гміна Лішки, Гебултів). Найближча
  дзельниця ввела б в оману; адреса й так показує, де клуб. Межі координат у Zod не змінено —
  обидва клуби в них уміщаються.
- **Тестовий клуб не додано.** dev, preview і production ділять одну БД (запис 0.18), тож його
  побачив би кожен на `/clubs`, а завантажувач клубів не видаляє — прибирати довелося б вручну.
  e2e-тести створюють і прибирають власні клуби.

**Наслідки:** нові клуби додаються дописуванням у `clubs.json` і `pnpm clubs:load` — upsert за
`slug` не чіпає вже завантажені. Підписи `PARTIAL` і `ARTIFICIAL_CLAY` для показу додасть 2.8
разом з рештою. `krakow-tennis-clubs.json` і `clubs_v2.json` лишаються поза git.

## 2026-10-09 — Синхронізація списку клубів і карти (задача 2.7)

**Як зроблено:** вибраний клуб — стан у `ClubsView` (`{ id, from: "list" | "map" }`), який
список і карта читають через контекст `components/club-selection.ts`. Клік по картці в списку
центрує карту (не ближче, ніж зум 15) і відкриває попап; на телефоні ще й перемикає на карту.
Клік по маркеру підсвічує картку і прокручує до неї список; закриття попапу знімає вибір.

**Чому так:**
- **Контекст, а не пропси.** Список і карта приходять у `ClubsView` слотами з серверної
  сторінки, тож пропсами стан до них не донести. Поза `ClubsView` контекст порожній, і карта
  працює сама по собі — 2.9 перевикористає її для оферт.
- **`from` у стані.** Реагує лише протилежна сторона: клік у списку не прокручує список, а клік
  по маркеру не рухає карту (Leaflet сам відкриває попап).
- **Картка — кнопка, «Details» — окреме посилання.** Вкладати посилання в кнопку не можна, а
  головна дія на `/clubs` — побачити клуб на карті. До сторінки клубу ведуть і «Details», і
  попап. Через це `ClubList` став клієнтським компонентом — дані він і далі отримує від сервера.
- **`invalidateSize()` перед центруванням:** на телефоні клік щойно показав приховану карту, і
  без нового виміру Leaflet центрує за старим розміром 0×0 (та сама проблема, що в 2.6).

**Перевірено:** e2e `clubs-sync.spec.ts` (список → карта, маркер → список, телефон). Тест
прокрутки падає, якщо прибрати `scrollIntoView`.
